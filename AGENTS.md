# Noten

Windows-native Markdown note app built with Tauri v2, React, and TypeScript. The app is Tauri-only — do not add browser fallbacks unless explicitly requested.

Three documents split the work: `docs/architecture.md` is the high-level map (repository layout, runtime boundaries, persistence model, sync flow, native/release layers), this file holds implementation invariants — the "do not do X, because Y" rules — and `README.md` holds user-visible behavior. Update each in the same change that invalidates it.

## Editor and Markdown

- The Markdown string is the serialization format and single source of truth on disk. A single persistent Tiptap v3 instance with `@tiptap/markdown` provides WYSIWYM editing, and stays readonly until the first document loads.
- Use the official `@tiptap/markdown` API only: `editor.getMarkdown()`, `editor.commands.setContent(value, { contentType: "markdown" })`, and `contentType: "markdown"` at init. Do not use community-package APIs such as `editor.storage.markdown.getMarkdown()`. Import menus from `@tiptap/react/menus` and `Markdown` from `@tiptap/markdown` — v3 paths, not v2 examples.
- Markdown is cached in `useMarkdownState.markdownRef` (`getCachedMarkdown` / `primeMarkdown`). Tiptap's `onUpdate` marks the cache stale; `scheduleAutoSave`'s `createSnapshot` refreshes it. Any imperative content load must call `primeMarkdown(md)` — `resetDocState` does this centrally.
- `TiptapEditorHandle.openDocument({ noteId, filePath, markdown, reason })` is the normal load/switch path; it restores a cached per-document ProseMirror `EditorState` when the Markdown signature still matches, keeping at most 20 sessions for selection and undo history. `setContent(md)` is the fallback wrapper. Call `invalidateDocumentSession(noteId, filePath)` before a deleted or identity-invalid session could be reused.
- The `Markdown` extension must stay configured with `createFastMarked()` from `src/extensions/fastMarkdownLexer.ts`. Stock marked's inline lexer is O(n²) on a single large block dense with code spans, links, HTML, or escapes — a multi-million-char note on one line froze the app for minutes. `FastLexer` builds the inline mask in one linear pass and its output is byte-identical, so do not revert to the bare extension. `fastMarkdownLexer.test.ts` fuzzes token-tree equivalence against stock marked; when a marked upgrade reshapes `Lexer.inlineTokens`, re-transcribe only the main tokenization loop.
- Clipboard `text/plain` goes through `sliceToPlainText` (`src/utils/clipboardText.ts`), joining block boundaries and hard breaks with a single `\n` so pasted text matches the on-screen line count. Only `text/plain` is overridden — `text/html` stays with ProseMirror, so rich targets keep formatting and in-app paste round-trips via `data-pm-slice`.

## Persistence

- `libraryStore` is the canonical in-memory library state. Every docs/groups/trash/active mutation must pass through its revisioned commit adapters; React arrays and `activeIndex` are projections, while active identity is stored as `activeNoteId`. Store snapshots own frozen copies, so never mutate a snapshot entity in place. Window-sync and watcher paths use their explicit `remote` / `reconcile` adapters — do not route them through `local`, because persistence must not turn observed state into a new local intent. `useWindowSync` takes a single `commitLibraryFromRemote(updater)` and expresses each event as one store updater that may change docs, groups, trash, and `activeNoteId` together (it returns `null` when nothing changed, so editor side effects run only after a real commit). Do not reintroduce `setActiveIndex` calls nested inside a `setDocs` updater — the store no longer buffers them; a change that touches docs and active identity belongs in one updater. Active identity is an id, so a docs-only commit that removes or reorders other notes needs no index bookkeeping. `useFileSystem`'s docs commits go through `sortAndPersistDocs(buildDocs)` as functional deltas keyed by id, recomputed against the store's `prev` — never commit an absolute docs array captured before an await, because a provision adoption, a doSave commit, or a peer event landing during the disk I/O would be erased by it. Groups commits follow the same contract (`useNoteGroups.persist(update)`, the prune, `newNote`, `importFiles`): functional deltas against `prev`, group tombstones recorded from the ids the commit actually dropped, and the broadcast carries the CHANGE, never an array. `groups-updated` is a delta like `trash-updated`: `{ upserted, removedIds, membership }`, where upserts carry the shared meta (no `collapsed` — per-machine, no `noteIds` — carried as membership ops) and are merged per field by the same clocks `mergeGroupEntries` uses on disk (name via `updatedAt`, order via `orderUpdatedAt`, `deletedAt` never un-set); removals are plain ids because group ids are uuids that are never reused, with a session `retiredGroupIds` set refusing a late out-of-order upsert's resurrection; membership ops `{ noteId, groupId | null, at }` apply with set semantics gated by a per-note clock (`lastMembershipAtByNote`, self-recorded at emit like the doc body clock). Senders compute the delta with `diffGroupsDelta(prev, committed)` from the updater's own prev — a value diff, never a reference diff (the store adapter clones every entry) and never the post-hoc latest snapshot. Intra-group `noteIds` order is deliberately not propagated: no consumer renders or persists it. The one sanctioned absolute commit is the watcher's reconcile result (`performReconcile` in `useFileWatcher.ts`): it baselines docs/groups from `libraryStore.getSnapshot()` — never from `docsRef`/`groupsRef`, which lag store commits by a render, so a peer commit whose render hasn't flushed would be invisible to a ref-identity check — and re-reads `libraryStore.getToken()` (revision + directoryGeneration) immediately before the synchronous setDocs/setGroups pair, abandoning and retrying on any movement. The watcher's group reload (`reloadGroupsFromDisk`) is NOT absolute at all: it applies the raw `.groups.json` + sidecar state through `mergeDiskGroups`, a pure clock merge inside a functional updater (same per-field rules as `mergeGroupEntries` and the `groups-updated` receiver), where the tombstoned/absent distinction is load-bearing — a disk tombstone removes the group, a merely-absent entry keeps the locally created one — and unwritten local intents (`pendingTombstones`, `pendingGroupMembership`) win over disk, or a reload racing an unwritten delete would resurrect the group and cancel its pending tombstone at persist time. Every path that resolves membership from sidecars must consult `pendingGroupMembership` the same way — `mergeDiskGroups`, `applyMetaChange`, and `reconcileFolder`'s `hydrateGroupMembershipFromMeta` (which takes the live map, since it resolves at the END of a multi-second pass) — because a peer rewriting a note's sidecar for an unrelated reason carries that note's OLD `groupId`: its own persist reads `groupId` from disk, not from the membership delta it just received. The rule is pending-wins-unconditionally, matching `resolveGroupSnapshot`; a clock comparison would have to change all four sites together — those three readers plus `resolveGroupSnapshot`, the writer — or the store and the write would settle on different groups. A remote `trashedAt` still ungroups, ahead of any pending intent, at every one of them. `reconcileFolder` consults the live map AND a copy taken with its sidecar read: live alone loses an intent the persistence chain consumes mid-pass (the sidecar it wrote is newer than the `allMeta` in hand, and reverting it makes no store commit for the drift guard to catch), while the at-read copy alone would miss an intent added during the pass.
- Manifest queue entries contain only a requested store revision and directory generation. The persistence job must read `libraryStore` when it executes; never capture a full docs/groups/trash array in the queue. Close and migration use `flushPersistence()`, which repeats if a newer revision commits while the barrier drains. A migration enqueues that barrier, raises `migrationInProgress` synchronously, and only then awaits it, so no later old-directory job can slip between a successful drain and the copy.
- Hydration (`useNotesLoader`'s load effect) is **generation-bound, not revision-bound**: its commits go through `commitLibraryForGeneration` and are rebased onto the current snapshot by `mergeHydratedLibrary`. The rebase covers docs, groups, AND trash: disk wins wherever the epoch observed no concurrent change, while a peer body newer than the disk read, an entity the loader never seeded (peer-created note, peer group, peer trash entry), and a peer's deletion all survive the stale read. Provenance is recorded live by the loader's epoch watcher (`HydrationEpochState`: seeded / projection / deleted ids for docs, seeded / touched / removed group ids, seeded trash ids and the `trashedAt` of each retired trash incarnation), never inferred from the data — an empty body is a legitimate document state, and "missing from the store" means deleted-by-a-peer or not-yet-projected depending on what the epoch saw. Groups carry no reliable version (`updatedAt` is optional) so the epoch record decides; trash uses `trashedAt`, matching the incarnation rule the `trash-updated` receiver applies. Do not gate hydration on revision equality — window-sync handlers stay live during load, and aborting on a foreign commit leaves the manifest-cache projection (empty bodies) as the canonical library. While a load is in flight, `hydrationInProgress` makes `flushPersistence`/`persistLatestLibrarySnapshot` no-ops (the projection is not user state and the write snapshots are unseeded, so a close-time flush would rewrite every sidecar from stale cache values); the loader persists the hydrated result itself. A `runPersistenceTransaction` requested mid-hydration (the sidebar already shows cached notes) is parked on the persistence chain until the load settles and then runs against the hydrated snapshot — only a real migration returns `invalidated` outright. The loader path must therefore never await the chain (`saveManifest`, `flushPersistence`, `saveNoteMetadata`, a transaction) or it would deadlock behind a parked job. The effect's deps are only `enabled`/`reloadKey` — locale and sort order are read at load start — and its cleanup marks a torn-down load restartable rather than leaving `isLoading` stuck.
- Settings updates are serialized per window and re-read/merged with the on-disk settings before each atomic write, so unrelated changes from another window survive.
- Only note bodies, sidecars, groups, assets, trash, and conflicts belong in the shared notes directory. Per-machine state (`settings.json`, `ui-state.json`, `manifest-cache.json`, `machine-id`, `migration-journal.json`, `crash.log`) stays in app data; the active note and group collapsed state are per-machine UI state, not shared sync state. Sidebar open/close state and width live in localStorage.
- Group membership carries its own `groupUpdatedAt` clock so group moves resolve independently of body last-write-wins. The shared `color` label (a fixed 7-color palette in `src/utils/noteColors.ts`) syncs like `pinned` — independent metadata that propagates even while the body is locally dirty — and does not bump `updatedAt`.
- Local title/pin/color mutations stamp per-note field clocks. Autosave compares requested, execution, and post-write clocks so a delayed metadata patch cannot overwrite a newer local intent (including ABA changes); clocks are acknowledged only after a durable writer succeeds, so a failed full persist remains retryable.
- Group entries carry independent name/update and order/order-update clocks plus a 30-day deletion tombstone. Membership stays in each note sidecar; the group deletion mutation sequence prevents stale queued saves from cancelling a newer tombstone.
- Notes-dir migration commits in the order copy → persist `notesDirectory` → clear source (`migrateNotesDir(..., { clearSource: false })` + `clearMigratedSource`), so a crash at any point leaves either the old dir authoritative or duplicate data — never a partial-only state. A 5s ack timeout or failed drain keeps the source for journal-based deferred cleanup instead of blindly clearing it; a 2s heartbeat and 15s peer watchdog release blocked windows if the migrator disappears.
- A failed use-selected-only migration captures `LibraryData` before changing settings and rolls the directory cache back with `restoreNotesDir`, which seeds that snapshot into a new hydration epoch. `setNotesDir` is idempotent for the same normalized directory, and `resetNotesDir` is idempotent when the directory cache already points at the default directory and the store is bound, so the settings effect that follows the revert (custom path or `""`) cannot clear the restored store.
- `appDataDir()` may not include a trailing separator; always check before joining paths.
- Local cache tracks `imageAssetMigrationV1CompletedAt` per notes directory for the one-time image asset migration.

## Capability Surface

Noten's privacy posture is "your notes never leave the disk," and it should stay verifiable through the Tauri capability allowlist in `src-tauri/capabilities/default.json`:

- File access uses the broad `fs:read-all` / `fs:write-all` commands but is constrained by `fs:scope` to `$APPDATA`, `$APPLOCALDATA`, and `$HOME`. Do not widen this scope without a concrete need.
- There is no HTTP-client plugin. The only outbound network is `tauri-plugin-updater` (checks GitHub releases) and `opener` (hands links to the system browser; it does not transmit note content). Do not add `http:` or other network permissions just to make a feature easier — a local-first note app should not phone home.

## Note Lifecycle and Folder Sync

- Body `.md` writes are fail-closed (`atomicWriteText(..., { failClosed: true })`): a tmp/rename failure throws instead of degrading to a non-atomic direct overwrite, so the doc stays dirty and retries rather than risking a truncated source of truth. They are also serialized per-doc inside `doSave` (`saveTailByDocRef`) so two overlapping saves never write the same `${path}.tmp`; only the write is locked — backup and the targeted note-metadata commit stay parallel. Autosave must not replay an unrelated full `docs` snapshot: its metadata writer preserves the disk lifecycle plus independent pin/color/group fields and updates only the saved note.
- Cross-window `doc-updated` events carry body content and its `updatedAt`, not titles. Title ownership stays with sidecar metadata and `doc-renamed`; otherwise a delayed body event can roll a newer manual rename back.
- Body recency on that channel is tracked by `useWindowSync`'s per-doc body clock (`lastBodyAtByDoc`, fed by `emitDocUpdated` and by every peer body applied), not by the doc's `updatedAt` — renames and pin/color writes bump `updatedAt` without touching the body, which is why applying a remote body keeps `max(updatedAt)`. A body event strictly older than that clock is dropped: event delivery is unordered across source windows, and applying the loser would leave content and `updatedAt` describing different revisions, so the next local save would write the stale body back over the newer one. The clock is forgotten on delete so a restore reusing the id is not blocked.
- `trash-updated` carries the CHANGE a window made (`{ added, removedIds }`), never its whole trash array. A snapshot broadcast makes every receiver adopt the sender's view wholesale, so a trash/restore/purge the receiving window did concurrently is silently undone and an out-of-order event resurrects entries whose files are already gone. `emptyTrash` therefore announces the entries it actually purged, not "the trash is empty". Removals carry `{ id, trashedAt }`, not a bare id: the id names the note, not the trash incarnation, so a restore-then-re-trash pair delivered out of order would otherwise let the late restore delete the newer entry. A receiver drops an entry only when its `trashedAt` is at or below the removal's. The receiver applies the delta to its own list, appending unseen entries at the end (where a local trash would put them) and keeping the newer `trashedAt` when both sides hold the same id.
- Auto-save uses `activeDocRef` (sync ref) to track the active document, not React state's `activeIndex`, to prevent wrong-doc writes after rapid switching. `hasPendingChangesRef` tracks whether `scheduleAutoSave` ran, so `flushAutoSave` can skip view-only documents.
- `notifyActiveDoc(id, filePath)` must be called in every code path that switches the active document (switchDocument, newNote, importFiles, duplicateNote, restoreNote, and the active handoff in `deleteNotes`).
- `flushAutoSave` returns an explicit `FlushResult` (`saved` / `provisioned` / `clean` / `failed`), never a boolean: "is the content on disk" and "may the caller mark its pre-flush docs snapshot clean" are different questions. Provisioning a dirty pathless active doc writes the body but also adopts a new `filePath`, so it reports `provisioned` — `flushLeftDocClean()` excludes it (a stale snapshot entry still has `filePath: ""`, and marking it clean would orphan the file and blind `hasUnsaveableChanges`), while `deleteNotes` accepts it and refuses only on `failed`. `restoreNote` never aborts on the flush result — the leaving doc is not the subject of the transition and afterCommit captures the editor's latest input before repointing.
- `deleteNotes(ids)` is the batch deletion core. It flushes each target independently, quarantines new body/provision writes, and runs the meta-first tombstone/body move on the shared persistence chain. Only targets whose transition is durable enter the single generation-bound docs/groups/trash/active commit; intent finalization and the forced latest projection follow that commit. A failed body copy rolls the sidecar back when possible; if rollback also fails, the durable tombstone wins and the rooted body is left for reconcile rather than removed. Both delete and restore read the previous sidecar through `readPreviousMeta`: a sidecar that exists but cannot be read or parsed (cloud placeholder, AV lock, truncated peer write) does not block the transition — the meta is rebuilt from canonical state, logged as `META_READ_FAILED`, and a rollback then repairs it from canonical state instead of removing it as if it had never existed. `deleteNote(index)` is a wrapper. `cancelDocSave(docId)` cancels pending autosave timers for one document and prevents orphan writes after delete.
- `renameNote` flushes each back-link doc's pending/in-flight save (`flushDocSave`) before rewriting `[[OldTitle]]` links, then computes non-active rewrites from the on-disk body (the in-memory copy can lag a just-landed background save). Docs whose flush or read-back fails are skipped entirely so memory never diverges from disk. Rename updates title metadata (and sets `customName`), not the underlying `.md` file path.
- `onCloseRequested` in App.tsx drains before window close: body saves (`flushAutoSave` → `awaitInFlightSaves` → `flushPendingSnapshots`) then the manifest queue (`flushManifest`, covering metadata-only writes like pin/color/group/rename that are otherwise fire-and-forget). It blocks the close (preventDefault + error dialog) if anything still failed to persist. A `.groups.json` write failure must propagate, not be swallowed, so this gate and the migration ack see it.
- `reconcileFolder` does not delete a `.meta/<noteId>.json` the instant its body file is missing — on a mid-sync cloud folder the sidecar can arrive before its body. An orphan meta is deleted only after a per-id grace (observed bodyless on a prior non-bulk pass AND first observed at least `ORPHAN_META_GRACE_MS` / 90s ago), and the whole sweep is skipped when many metas are bodyless at once (bulk guard — likely mid-sync).
- Remote body conflicts are last-write-wins with previous remote bodies backed up under `.conflicts/`, which travels with the notes directory on a folder change or migration. A `merge` migration also backs up an about-to-be-overwritten destination body there.
- Empty notes (no content, no customName) are auto-deleted when leaving via `pruneEmptyCurrentDoc` (switchDocument, importFiles, duplicateNote; `newNote` and `restoreNote` apply the same rule inline — `willReplace` and the restore transaction's `pruneLeavingDoc`). Pruning removes both the `.md` body and its sidecar so no orphan metadata is left behind.
- Soft delete moves the body to `.trash/<noteId>.md` and records `trashedAt` / `trashedFromPath`. Restore keeps note assets; permanent delete and the 14-day purge remove body, metadata, and `.assets/<noteId>/` only after validating the note id.
- `restoreNote` is the mirror of `deleteNotes` on the same persistence chain: it reads the execution-time trash entry, awaits the live sidecar write BEFORE copying the body back (Windows `copyFile` preserves the source mtime, so a reconcile that still reads `trashedAt != null` would move the body straight back to `.trash`), rolls the sidecar back to its tombstone if the copy or read-back fails, removes the trash copy only once the restore is durable (reconcile never sweeps `.trash`), and publishes docs/groups/trash/active as one generation-bound commit. A sidecar write failure fails closed — no body copy, no commit. The empty-leaving-doc prune runs inside that transaction (its id is a bound target) so the prune and the restore land in the same commit. Once the disk transition is durable the commit is applied against whatever the store holds, never refused because a peer window rebuilt the trash entry in the meantime; likewise the pre-copy re-check compares the trash entry by id and `trashedAt`, never by object identity, because a peer `trash-updated` event rebuilds every entry object.
- Treat note ids read from cloud or legacy data as untrusted path segments. `isValidNoteId` must guard `.md`, `.meta`, `.assets`, `.trash`, and recursive-delete paths before filesystem operations.
- `Ctrl+O` imports selected files into the app notes directory as managed internal notes with new ids, treated identically to other internal notes afterwards.
- Pinned notes sort before unpinned ones, with the active sort order preserved within each partition; in groups, pinned notes stay at the top of that group.

## Wiki Links and Titles

`[[Title]]` names its target by title alone, so duplicated titles need one agreed resolution rule, shared by every consumer:

- `findDocByTitle` orders candidates by `createdAt` ascending with the note id as tiebreaker — never by position in `docs`, which is the sidebar sort order (under the default `updated-desc`, editing one of two same-titled notes would otherwise silently re-point every link at it).
- When the link's own note is in a group, a candidate in that same group wins. `findDocsByTitle` exposes the full candidate list for ambiguity checks.
- The click handler resolves the target and hands `navigateToDoc` an **id**. Do not re-resolve a title on the App side; two lookups can disagree.
- `renameNote` skips back-link rewriting entirely when the OLD title was shared by another note: `[[Old]]` cannot be attributed to one target, and rewriting would re-point links belonging to the other note. It returns `RenameNoteResult.linkRewriteSkipped` and App.tsx surfaces the transient notice.
- `normalizeNoteTitle` (`src/utils/noteText.ts`) is the single definition of "same title" for link resolution, duplicate detection, and rename.
- `customName` on a document means the user manually renamed it; auto-title derivation is permanently disabled for that document.

## Images

- Image sources are note-local relative asset paths (`.assets/<noteId>/<hash>.<ext>`) on insert, replace, drop, and paste. Legacy base64 is still accepted (`allowBase64: true`) and migrated on startup once per notes directory.
- Image NodeViews share one per-editor `transaction` subscription (`registerImageSelectionSync` in `ImageView.ts`) that re-syncs selection outlines only when the node-selected position or readonly flag changes. Do not re-add a per-NodeView `editor.on("transaction")` listener — that made selection bookkeeping O(images) on every keystroke.
- Renderable image sources use a bounded LRU cache (128 entries / 16 MiB). Clear it whenever the active notes directory changes, resets, or rolls back so one directory's asset data cannot leak into another session.
- Image Markdown serialization must use `serializeImageMarkdown` so `src`, `alt`, and `title` are escaped correctly for their Markdown/HTML context. When `width`/`height` are set, `renderMarkdown` emits `<img>` HTML to preserve dimensions through round-trips.
- On insert, images are capped to 560px width via `clampImageDimensions`. Height is always `auto` in CSS — only width is set in px, to prevent aspect-ratio distortion on narrow viewports.
- `createImageNodeView` owns resize handles, drag reorder (6px `pointerdown` threshold → `startReorder()`, single undo step), context menu, and asset-source rendering. Ctrl+C on a selected image copies the image blob, not HTML.

## Tables and Mermaid

- Tables use Tiptap v3 table extensions with `lastColumnResizable: false`, so dragging an inner column redistributes width instead of growing the table past the editor width.
- Empty table cells may serialize through `&nbsp;`; `stripTableCellNbsp` removes placeholder-only leakage before load/save while preserving a user-authored literal `&nbsp;`.
- Mermaid diagrams are `mermaid` code blocks rendered by the `MermaidCodeBlock` NodeView; keep its source/preview toggle and SVG/PNG export controls inside the NodeView. User-visible Mermaid labels go through `src/i18n.ts`.
- Exported SVGs round-trip their source: `mermaidExport.ts` embeds the original Mermaid source via `embedMermaidSourceInSvg` (`src/extensions/mermaidSourceMetadata.ts`, stored in `<metadata>` under a private namespace), and `ImageDrop.ts` restores a marked SVG back into an editable Mermaid block via `extractMermaidSourceFromSvg`.

## Note Export

- Markdown export writes `editor.getMarkdown()`; PDF export serializes the live editor DOM through headless Edge (`print_to_pdf`).
- The editor DOM also carries transient decorations, so PDF export must go through `cloneEditorContentForExport` (`src/utils/exportHandlers.ts`), which unwraps `.search-match` / `.search-match-active` spans on a *clone*. Without it an open find bar prints its highlights into the PDF. Add any future decoration class to `DECORATION_SELECTOR`.
- `print_to_pdf` temp files are per-invocation (pid + timestamp + counter): a fixed name let two windows exporting at once overwrite each other's HTML and render the wrong note. They hold the full note body in plain text, so every return path must delete them.
- Edge is spawned, not `output()`-ed: the run is bounded by `PDF_RENDER_TIMEOUT` and the child is killed on expiry, so a wedged headless Edge cannot leave the `invoke` pending forever. Its stderr goes to a file rather than a pipe — nothing drains a pipe while we poll for exit, so a chatty child could block and then be killed spuriously.

## Editor Decorations

Per-keystroke work in the editor must be incremental — no plugin or observer may re-derive whole-document state on every transaction:

- Focus mode (`FocusMode.ts`): per-selection cost is constant regardless of document size. The plugin never walks the document (no `doc.descendants` on any path); the current block's boundaries come from the resolved selection head (`$head.before(1)` / `$head.after(1)`). The decoration set holds at most one node decoration; same-block caret moves return the previous plugin state by reference, and same-block edits remap through `tr.mapping`. Dimming every other block is pure CSS. The active flag lives in extension storage so it survives `view.updateState()` note swaps, which emit no transaction.
- Outline recomputation (`useOutline` in `OutlinePanel.tsx`) coalesces to one pass per frame via rAF. Document change is decided by doc-node identity (`editor.state.doc !== lastDoc`), not `tr.docChanged`, because note switches arrive via `view.updateState()` without a transaction. Selection-only frames skip the heading walk; after a walk the result is compared by `${level}:${pos}:${text}` signature so unchanged outlines skip setState. The panel stays mounted for its width transition, but its subscription and full extraction run only while open, and opening recomputes in a layout effect so a document changed while closed never flashes a stale list.
- In-editor find (`SearchHighlight.ts`): `findSearchMatches` is the single match finder shared by `SearchBar` and the plugin. The full match list backs the counter, next/prev, and replace-all, but only `SEARCH_DECORATION_CAP` (2000) decorations are drawn — `selectMatchesToDecorate` picks those nearest the visible range, fed by a scroll-driven plugin `view`. Keep the count truthful and the drawn set bounded; do not decorate every match.
- Wiki-link "missing link" decorations (`WikiLink.ts`): a target's existence changes only via the forced refresh meta (`refreshWikiLinkDecorations`, dispatched from `App.tsx` when the docs/title set or locale changes), so a plain edit remaps the existing `DecorationSet` and recomputes only the changed range. `findDocByTitle` is O(1) via a title map cached per `docs` array reference.
- Anchor links (`AnchorLink.ts` + `src/utils/headingSlug.ts`): a link mark whose href starts with `#` jumps through the same `handleOutlineJump` path the outline panel uses. Fragment resolution walks the document only at click time and once per link-popover session for `#` autocomplete — never per transaction. The popover stores GitHub-style slugs (`#서론-개요`) so serialized destinations never contain spaces, but `resolveHeadingFragment` stays tolerant of raw titles and percent-encoding — on-disk markdown is never rewritten to conform.

## Logical Lines

The status bar's line count, its caret row, and Go to Line all use the *logical line* defined in `src/utils/documentLines.ts`: one line per textblock plus one per newline character or hard break inside it. Keep the three readouts on the same definition — the number the status bar shows must be the number Go to Line accepts.

- Counting top-level blocks (`doc.childCount`) instead made a ten-item list and a twenty-line code block read as one line.
- A jump target goes through `selectionForLinePos`. A line that *is* a leaf block resolves to a block position, where `TextSelection.create` does not throw but yields a selection whose parent has no inline content, so the next keystroke inserts a stray paragraph. That fallback assumes every block leaf in the schema is selectable; a non-selectable block atom would silently jump to the wrong line.
- `buildLineIndex` is O(document): cache it against `doc` identity (selection-only transactions reuse the node), never rebuild per caret move, and coalesce doc-change rebuilds to one per frame — both the status bar and Go to Line subscribe to every transaction. The same walk produces character and word counts; taking them from `doc.textContent` both allocates a second copy of the document and fuses each block's last word to the next block's first.

## Context Menus

- Editor/NodeView DOM context menus use the shared helpers in `src/utils/contextMenuRegistry.ts` (`createMenuShell`, `createMenuItem`, `createMenuSeparator`) and its singleton registry, so only one is open at a time. React sidebar and app menus have their own Fluent-based state and focus handling; `TextContextMenuContext` is the shared text context menu interface for Tiptap.
- All menus are clamped to the viewport via `clampMenuToViewport()`, accounting for the 25px status bar.
- The text menu's link item routes through `editor.storage.linkPopoverShortcut.trigger` — the same entry point as Mod-k — so popover behavior stays single-sourced.
- Shortcut hints are shown in context menus with one unified style across all menus (opacity 0.45, 12px, 24px left padding).

## UI Conventions

- Use Fluent UI v9 for app chrome and `@fluentui/react-icons` in React. Raw DOM NodeViews and context menus may use the existing inline Fluent SVG-path helpers. Do not introduce unrelated icon sets or browser-style controls.
- The editor surface (`.ProseMirror`) reads shared colors from CSS variables in `src/styles/theme.css` and is capped at `--editor-max-width`, centered, with the surrounding area still clickable/scrollable.
- All user-visible strings go through `src/i18n.ts`. Do not hardcode locale checks inline except for the intentionally human-written bilingual release-note block in `SettingsModal.tsx`; keep other necessary branching inside centralized formatters/adapters.
- Unless `pinEditorToolbar` is set, toolbar and status bar visibility is driven by scroll position, not editor mode: visible at the top, hidden after scrolling down past a short threshold, shown again on scroll up or a click inside the editor.
  - Focus mode (F8) pins the chrome hidden while active, regardless of scroll direction. This is intentional design — chrome popping in and out contradicts the mode — not a scroll-state bug.
  - Programmatic scrolls that must not flash the chrome (outline jumps) freeze visibility via `lockEditorChrome(ms)`; user wheel/mousedown input drops the lock immediately (`unlockEditorChrome`).
- The sidebar's flat lists (All Notes, search results, colour filter) render every note at once and are drag-inert, so their rows carry `content-visibility: auto` (`docItemSkippable`). The grouped root view must stay fully laid out — drag-to-group and the FLIP animations measure real geometry. Drag-to-group works only in the root view; the colour filter reuses the search flat-list rendering path, so drag is inert while filtered.
- Sidebar shortcuts (Ctrl+D, Ctrl+R, F2, Ctrl+E, Ctrl+Alt+P, Ctrl+Alt+C, Delete) are active when the last mousedown **or focusin** landed inside the sidebar, tracked via `data-sidebar-active` on `document.documentElement`. Focus counts because keyboard-only users reach the note list with Tab and never emit a mousedown; focus leaving the sidebar deactivates it (a blur to `document.body` does not).
- Those shortcuts act on the note the user pointed at, in this order: the right-clicked note while a note context menu is open, else the row that took the last mousedown/focusin, else the active note. The pointed row is remembered as a note **id** and resolved to an index at keypress time, because sorting can move a row in between (and a vanished row must resolve to nothing rather than to whatever now sits at that index). Targeting the active note instead would act on the open note while the user is looking at a different, focused row.
- Delete additionally requires that a pointed row or context-menu target actually resolved — it never falls back to the active note. Sidebar chrome, empty space, and a vanished row all leave it inert, because a destructive shortcut must not reach a note nobody pointed at.
- Editor shortcuts (`Ctrl+Shift+X` strike-through, `Ctrl+G` Go to Line, `Ctrl+H` Find and Replace, `Ctrl+Shift+O` table of contents, `F8` focus mode) are handled at the window level via `useKeyboardShortcuts`, not inside individual editor keymaps. `F8` is ignored while a modal dialog (role="dialog") holds focus; `Ctrl+O` (import) needs its explicit `!shiftKey` guard so `Ctrl+Shift+O` never falls through to it. `Ctrl+P` stays blocked, reserved for a future quick switcher.
- Browser/WebView shortcuts that would interfere with app behavior are blocked: reload, DevTools, print, source view, caret browsing, zoom, and browser back/forward. Ctrl+R is unblocked when the sidebar has focus (rename). Ctrl+S is swallowed as a no-op since autosave persists continuously.
- Toggling/resizing the sidebar updates the OS window min-size and grows a too-narrow window to fit (`ensureWindowFitsSidebar` in `App.tsx`). This is skipped while maximized or fullscreen — mutating window size there pops it back to windowed and shifts position on Windows — and the deferred min-size is re-applied on restore, detected via `onResized`.
- Note sort order supports `updated-desc` (default), `updated-asc`, `created-desc`, `created-asc`, `title-asc`, `title-desc`. Legacy `recent-first` / `recent-last` are auto-migrated on load.

## Local Dev Workflow

- `npm run tauri:dev` for normal development; it runs `scripts/prepare-helper.ps1` to prepare `src-tauri/resources/maintenance-helper.exe`, then starts `tauri dev`. `scripts/prepare-helper.ps1 -Release` builds only a release-mode helper, without bundling.
- `npm run check` chains `typecheck` + `lint` + `test`; `.github/workflows/ci.yml` runs the same on every push and PR to `main`.
- `npm run test:smoke` runs just `src/smoke/` — the cross-module suite described under Quality Gates. It is a subset of `npm test`, useful as a fast first signal after touching the store, persistence, reconcile, or group-merge paths.
- `npm run test:perf` runs just `src/perf/` — performance guards for the loading, saving, note-switch, and memory-boundedness paths, defined in `docs/performance-testing.md`. They are regression tripwires, not benchmarks: deterministic data, best-of-three timing, budgets ~10x a dev-machine measurement. Also a subset of `npm test`.
- `node scripts/gen-notes.mjs --out <dir> --count <n> [--groups <n>]` writes a synthetic notes directory for measuring startup, sidebar, and search behavior at library sizes real test folders never reach. Development aid only; it refuses to overwrite an existing library without `--force`.
- `scripts/build-release.ps1` is a **local smoke test only** — it does not sign and is not what ships. It also fails at the Tauri step without `TAURI_SIGNING_PRIVATE_KEY` in env, because `bundle.createUpdaterArtifacts` is on.

## Quality Gates

- **ESLint** (`eslint.config.js`) enforces two narrow project invariants on top of TypeScript:
  - Durable writers (`metadataIO.ts`, `groupsIO.ts`, `conflictFileDetector.ts`, `migrateImageAssets.ts`) must call `atomicWriteText`, never `fs.writeTextFile` directly. Add new durable writers to the allowlist explicitly.
  - `FileStat.mtime` and `birthtime` cannot be bypassed via non-null assertion or `as` cast; the `Date | null` shape must be handled explicitly. Tests are exempt.
- **Contract tests** (`src/utils/contracts.test.ts`) cover cross-file invariants ESLint cannot express cheaply — e.g. every external `setNotesDir` / `resetNotesDir` call site must pass the reconcile state. Keep them grep-based and add one for each new regression class.
- **Smoke tests** (`src/smoke/`) are the only suite that runs the real modules together: two windows over one in-memory folder, driving the real `libraryStore`, `persistDecomposedState`/`loadDecomposedState`, `reconcileFolder`, and `mergeDiskGroups`. They exist for the stale-snapshot class — a commit computed from a snapshot that went stale across an await, erasing a concurrent change — which every per-module suite misses because each module is individually correct. The Tauri-bound layers (the metadata mutation clocks in `useNotesLoader`, `useWindowSync`'s event channel, React projections) cannot be imported outside Tauri and are deliberately NOT modelled, so these tests assert membership, group metadata, and note existence — never title/pin/colour LWW. `windowHarness.test-utils.ts` reimplements thin adapters that MIRROR named production hooks: when you change one of those hooks, re-check the adapter whose doc comment names it, and give each window its own `FileSystem` facade — `readAllMeta` caches by FileSystem identity, and sharing one object would hand the tests fresher sidecars than a real second window ever sees.
- **Fault injection** (`src/utils/fs.fault.test-utils.ts`, `wrapWithFaults`) reproduces OneDrive placeholders, AV rename locks, transient network errors, and `mtime: null` cases that the bare `InMemoryFileSystem` cannot.
- **Crash log**: fatal/recoverable errors flow through `NotenError` + `logNotenError` into `AppData/Roaming/com.noten.app/crash.log` (capped, per-component truncation in `formatLine`). `initCrashLog()` also captures uncaught `error` / `unhandledrejection` events.

## Release and Updater

Releases are fully automated by `.github/workflows/release.yml`, triggered by pushing any `v*` tag. Do not build shippable installers locally.

To cut a release:

1. Edit `package.json`'s `version`, then run `npm run sync-version`. The script propagates it to `package-lock.json`, `src-tauri/tauri.conf.json`, the four `Cargo.toml` files, and our entries in both `Cargo.lock` files. The `v…` label in `SettingsModal.tsx` reads `getVersion()` at runtime and needs no sync — add a new entry to the script only if you introduce another hardcoded version site.
2. Rewrite the SettingsModal changelog block (Korean + English). This is human-written copy and is intentionally not touched by the script.
3. Commit, push `main`, then `git tag -a vX.Y.Z <commit> -m …` and push the tag.

CI builds the helper, runs the commit-SHA-pinned `tauri-apps/tauri-action` v1 to produce signed updater artifacts, then builds and Authenticode-signs the bootstrapper. The result is a **draft** release that must be reviewed and **manually published** — only then does the in-app updater see it, because the endpoint (`.../releases/latest/download/latest.json`) resolves `latest` to the most recent *published* release.

- Production publishing requires `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, `CODE_SIGN_PFX`, and `CODE_SIGN_PFX_PASSWORD`. The Authenticode step is conditional when the PFX is absent, but an unsigned bootstrapper must not be published as a production release.
- The Tauri pubkey in `tauri.conf.json` must stay paired with the private key — rotating one without the other breaks updates for existing installs.
- Two installers exist per release: `noten-setup.exe` (the bootstrapper, what fresh-install downloads should link to) and `Noten_X.Y.Z_x64-setup.exe` (the raw NSIS bundle, present only because `latest.json` points at it as the update payload).
- The app performs one background update check after startup; SettingsModal can also check manually. On Windows with `installMode: quiet`, `useUpdater` calls `update.downloadAndInstall()`, then exposes a restart action calling `relaunch()`.

## Code Style

- PascalCase file names for components; camelCase for hooks; either under `src/extensions/`. Shared styles in `src/styles/`, shared utilities in `src/utils/`, tests colocated with the module they cover.
- Comments should explain non-obvious invariants, race/concurrency constraints, data-loss risks, or platform quirks. Do not add comments that restate nearby code, narrate ordinary control flow, or preserve temporary implementation history.
- Prefer short English comments in complete sentences. Avoid decorative section banners and numbered step comments unless they clarify a long algorithm. Keep JSDoc for exported APIs only when it documents behavior the type signature does not already make clear.
- A few shared utilities exist specifically to keep a rule in one place — prefer them over reimplementing:
  - `src/utils/concurrency.ts` — `mapWithConcurrency`, the bounded fan-out for startup body reads (an unbounded `Promise.all` over every note stampedes the IPC bridge and cloud-folder placeholder hydration).
  - `src/utils/docsSignature.ts` — `sortSignature`, the allocation-free change detector gating App.tsx's re-sort effect.
  - `src/utils/noteId.ts` — note id validation before use as a filesystem path segment.
  - `src/utils/migrationJournal.ts` / `migrationCleanup.ts` — crash-safe deferred cleanup of a migrated notes directory.
