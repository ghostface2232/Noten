# 에디터 성능 측정·분석·개선 계획 (2026-09-21)

큰 노트에서 초기 로딩, 문단 편집, 한글 입력, 이미지 로딩이 얼마나 걸리는지 **실제 앱에서** 측정하고, 지연이 어디서 왜 생기는지 CPU 프로파일과 브라우저 트레이스로 확인한 뒤, 그 근거로 개선 순서를 정리한 문서입니다. 측정 도구와 재현 방법은 [bench/README.md](../bench/README.md)에 있습니다.

요약:

- **로딩이 O(n²)였습니다.** 목록·표 토크나이저가 블록마다 남은 문서 전체를 줄 단위로 나눴습니다. 결과가 달라지지 않는 수정으로 1MB 로딩이 9.0초→0.5초(소설), 55.6초→0.8초(짧은 문단)가 됐습니다. **커밋 완료.**
- **코드블럭 입력이 키당 3.3초였습니다.** 하이라이트 플러그인이 모든 코드블럭을 다시 칠했습니다. 바뀐 블록만 칠하도록 바꿨습니다. **커밋 완료.**
- **상태바 글자·단어 수가 키마다 문서 전체를 다시 셌습니다.** 블록 단위 캐시로 바꿨습니다. **커밋 완료.**
- 이 세 가지를 고친 뒤 남는 가장 큰 비용은 JS가 아니라 **브라우저 엔진이 매 프레임·매 입력마다 문서 전체를 다루는 비용**입니다(페인트, 커밋, 선택 동기화, Windows IME 연동). 특히 한글 IME는 목록·표가 많은 1MB 문서에서 조합 한 번에 1초가 넘게 걸렸습니다. **블록 단위 `content-visibility: auto`** 실험에서 같은 입력이 5~25ms로 줄었습니다(다음 단계 1순위).
- **이미지가 많은 노트는 메모리와 시간이 모두 과도합니다.** 627장 노트에서 JS 힙 2.1~2.8GB, 전체 표시까지 24~41초가 걸렸고, 그중 15초가 메인 스레드의 base64 변환입니다.
- 측정 중 **기존 버그 2건**을 발견했습니다. 특정 마크다운에서 파서가 예외를 던져 노트가 열리지 않고, 표 셀 CSS 때문에 표가 많은 문서의 스크롤이 끊깁니다.

## 1. 측정 방법

### 1.1 환경

- **앱**: release Rust + production(minify) 프론트엔드 + WebView2(Chromium 153). `tauri dev`의 React 개발 모드는 실제보다 느려 쓰지 않았습니다.
- **격리**: 식별자 `com.noten.bench`로 따로 빌드해 `%APPDATA%\com.noten.bench`만 읽고 씁니다. 사용 중인 `com.noten.app`의 노트·설정·WebView2 프로필이 측정 전후로 바뀌지 않았음을 확인했습니다. 업데이터가 설치를 시도하지 않도록 버전은 99.0.0으로 고정했습니다.
- **구동**: CDP(Chrome DevTools Protocol)로 실제 입력 이벤트(키, IME 조합, 마우스 휠)를 넣었습니다. 입력한 글자가 자동저장으로 디스크 파일에 기록되는 것까지 확인해, 측정 경로가 실제 사용과 같음을 검증했습니다.
- **재현성**: 같은 조건을 다시 측정하면 로딩은 ±10% 안에서 재현됩니다(예: 100KB 소설 404ms / 408ms). 머신마다 절대값은 다르므로, 판단의 근거는 **같은 조건의 전후 비교**와 **크기에 따른 증가율**입니다.

### 1.2 자료

| 종류 | 내용 |
|---|---|
| novel-en | Project Gutenberg 소설 3권(전쟁과 평화, 오만과 편견, 셜록 홈즈) |
| wiki-en / wiki-ko | 영문 위키백과 15편, 한국어 위키백과 16편 |
| paragraphs | 한 문장짜리 문단 수만 개 |
| one-paragraph / one-line | 문서 전체가 한 문단 / 한 줄 |
| lists / headings / code / tables | 목록·체크리스트 / 헤딩 / 코드블럭 / 표가 많은 문서 |
| mixed | 위 요소를 섞은 작업 노트 |
| images | 약 2KB 문단마다 서로 다른 이미지 파일 1장 (100KB: 60장, 1MB: 627장) |

각 종류를 100KB / 1MB / 10MB로 생성했습니다(시드 고정, 재현 가능). 10MB 텍스트 노트는 현실적이지 않아, 판단은 100KB·1MB로 하고 10MB는 수정 후 크기에 비례해 버티는지 확인하는 데만 썼습니다.

### 1.3 지표

- **로딩**: 새로고침부터 노트 내용이 그려진 프레임까지(ready), 마지막 긴 작업이 끝날 때까지(settled). 3회 중앙값.
- **입력 지연**: 각 종류의 중간 블록(문단·코드블럭·목록 항목·표 셀)에서 키 35회. 키 이벤트 시각부터 다음 프레임이 그려질 때까지이며, vsync 대기(0~17ms)가 포함됩니다.
- **Enter**: 블록 분할.
- **한글 IME**: Windows IME와 같은 방식(자모마다 조합 갱신, 음절마다 확정)으로 "한글입력문장"을 3회 입력.
- **자동저장**: 입력을 멈춘 뒤 2.5초 동안의 긴 작업(디바운스 1초).
- **스크롤**: 휠 40회 동안의 프레임 간격.
- **원인 분석**: V8 CPU 프로파일(함수별 self time), Chrome 트레이스(페인트·커밋·레이아웃·히트테스트·IME 연동 등 JS 밖의 메인 스레드 작업), 앱 안에서 직접 잰 `getMarkdown()` / `markdown.parse()` 시간.

## 3. 지연 원인 (근거 포함)

### 3.1 로딩: 마크다운 토크나이저의 O(n²) — 수정 완료

- **근거**: 1MB 소설 로딩 CPU 프로파일 9.4초 중 `parseIndentedBlocks` 3.6초, orderedList `tokenize` 3.6초, table `start` 1.6초. 100KB→1MB에서 파싱 시간이 크기(10배)가 아니라 60~500배 늘었습니다.
- **원리**: marked는 블록 경계마다 모든 블록 확장 토크나이저를 "남은 문서 전체"를 넘겨 호출합니다. Tiptap의 taskList·orderedList 토크나이저와 table의 `start`는 목록이나 표가 여기서 시작하는지 판단하기 전에 `src.split("\n")`부터 합니다. 결과적으로 비용이 블록 수 × 남은 크기가 됩니다.
- **영향**: 문단·헤딩이 많을수록 심합니다. paragraphs 55.6초, headings 33.5초. 헤딩 바로 아래 빈 줄 없이 본문이 오는 352KB 문서도 파싱에만 67초가 걸렸습니다.

### 3.2 코드블럭: 하이라이트 전체 재계산 — 수정 완료

- **근거**: code-1m 입력 p50 3,318ms, 그중 JS가 키당 1,465ms.
- **원리**: `@tiptap/extension-code-block-lowlight` 플러그인이 다음 일을 합니다.
  - 커서 이동을 포함한 모든 트랜잭션에서 옛 문서와 새 문서 전체를 두 번 훑습니다(`findChildren`).
  - 선택이 코드블럭 안에 있으면 문서의 **모든** 코드블럭을 다시 하이라이트합니다.

### 3.3 상태바 글자·단어 수 — 수정 완료

- **근거**: 1MB 소설 입력 프로파일에서 `countRun` / `isSpaceCode`가 JS 1·2위였습니다.
- **원리**: 줄 수는 노드 단위로 캐시하고 있었지만, 글자·단어 수는 편집 후 매 프레임 문서 전체 텍스트를 다시 셌습니다.

### 3.4 세 가지를 고친 뒤 남는 비용: 브라우저 엔진의 문서 전체 작업

JS 수정 후 트레이스(메인 스레드 self time)를 보면, 남은 시간은 대부분 Chromium 쪽입니다.

| paragraphs-1m, 키 35회 | 시간 |
|---|---|
| `Commit` (메인→컴포지터) | 572ms |
| `Editor::SyncSelection` | 555ms |
| JS 전체 (`FunctionCall`) | 429ms |
| 레이아웃 | 334ms |
| 페인트 | 265ms |
| `GetSelectionOffsets` | 197ms |
| 컴포지팅 입력 갱신 | 185ms |

같은 문서의 한글 IME 72회 조합 갱신에서는 다음 순서입니다.

| 이벤트 | 시간 |
|---|---|
| `Edge_RunTask` | 4.1초 |
| `WidgetBase::WillBeginMainFrame` | 1.8초 |
| `Commit` | 1.1초 |
| `TypingCommand::InsertText` | 1.1초 |
| `GetSelectionOffsets` | 0.7초 |

- **해석**: 페인트·커밋·컴포지팅은 편집 영역 전체의 페인트/레이어 트리를 따라가므로 문서 크기에 비례합니다.
- **해석 (IME)**: 선택 동기화와 IME 연동(Windows TSF에 선택 위치·텍스트를 넘기는 경로)은 contenteditable 루트 기준의 텍스트 오프셋을 계산합니다. 커서 앞 텍스트 전체를 지나야 하므로 역시 O(문서)입니다.
- **한글에서 특히 느린 이유**: 조합 갱신마다 이 경로를 다시 타기 때문입니다. 영문 입력보다 5~10배 느린 원인이 이것입니다.

**실험**: 최상위 블록에 `content-visibility: auto`를 걸면 화면 밖 블록의 레이아웃·페인트·텍스트 순회를 브라우저가 건너뜁니다. 같은 빌드(§4 수정 3건 적용)에 CSS 한 줄만 바꿔 비교했습니다.

| 1MB | 입력 p50 | 한글 IME p50 | 로딩 | 스크롤 p95 |
|---|---|---|---|---|
| lists | 79.8 → **4.4ms** | 1,013 → **5.2ms** | 1.51 → 0.80초 | |
| code | 205 → **17ms** | 2,133 → **24.5ms** | 2.60 → 1.59초 | |
| tables | 128 → **19ms** | 1,383 → **17.6ms** | 1.82 → 0.83초 | 147 → 18.6ms |
| mixed | 75.5 → **21.9ms** | 878 → **78ms** | 1.40 → 0.92초 | |
| 100KB lists/code/tables/mixed | 약 10~18 → 3.5~18ms | 30~90 → **5~8ms** | 약간 감소 | 변화 없음 |

**모든 블록에 걸면 역효과가 납니다.**
- **원인**: `content-visibility: auto` 요소마다 브라우저 내부 IntersectionObserver가 붙습니다.
- **증상**: 한 문장짜리 문단 2만 개 문서에서 `computeIntersections`가 새 병목이 됐습니다(스크롤 p95 20→108ms).
- **결론**: 목록·표·코드·인용 같은 **컨테이너 블록에만** 거는 선택자가 답입니다(위 표가 그 결과). 문단·헤딩이 대부분인 문서는 변화가 없도록 설계했습니다.

### 3.5 이미지: 전부 즉시 읽고 base64 문자열로 보관

- **근거**:
  - images-1m 로딩 프로파일에서 `bytesToDataUrl` 15.3초(`String.fromCharCode` + `btoa`).
  - 전체 이미지 표시까지 24~41초, JS 힙 2.1~2.8GB.
  - 첫 텍스트 표시도 이미지 처리에 밀려 1.5초~18초로 들쭉날쭉했습니다.
  - 100KB(60장)도 전체 표시 2.2초, 힙 70~120MB(텍스트 문서의 5배)입니다.
- **원리**:
  - 이미지 NodeView는 생성 즉시(화면 밖이어도) 파일을 IPC로 읽고, 바이트를 base64 data URL 문자열로 변환해 `img.src`에 넣습니다.
  - LRU 캐시(128개/16MiB)는 캐시일 뿐이고, 각 `<img>`가 자기 문자열을 붙잡고 있어 메모리는 이미지 총량의 1.33배로 커집니다.
  - `decoding="async"`나 지연 로딩도 없습니다.

### 3.6 자동저장·노트 전환: 문서 전체 직렬화

- **근거**: 앱 안에서 직접 잰 `getMarkdown()`이 1MB에서 7~120ms(표 120, 목록 98, 혼합 84ms)입니다. 입력을 멈춘 뒤 자동저장 긴 작업 103~164ms와 일치합니다.
- **같은 비용이 드는 곳**: 노트를 떠날 때 세션 캐시 서명을 만들 때(`storeCurrentDocumentSession`)도 같은 직렬화를 합니다.
- **1MB에서의 비중**: 저장 경로의 I/O(충돌 확인용 전체 읽기, 쓰기, 감시기의 자기 쓰기 재확인과 해시)는 메인 스레드 비용이 수 ms 수준이라 아직 작습니다.

### 3.7 기타 확인된 비용

- **코드블럭 NodeView가 무겁습니다.**
  - 모든 코드블럭(머메이드가 아니어도)이 버튼 3개와 SVG 아이콘을 `innerHTML`로 만듭니다.
  - code-1m은 DOM 133만 개, 힙 274MB이고, 로딩 프로파일에서 `MermaidCodeBlockView` 163ms가 나옵니다.
  - 하이라이트 스팬 적용(`takeSpansForNode`)도 427ms입니다.
- **표 스크롤이 끊깁니다.**
  - 모든 `td`/`th`가 `position: relative`라 셀마다 페인트 레이어가 생깁니다.
  - 스크롤 뒤 호버 갱신 히트테스트가 레이어 수에 비례해, tables-1m 스크롤 40틱에 `HitTest` 6.8초가 걸렸습니다(p95 134~161ms).
  - `content-visibility` 실험에서는 이 문제도 18.6ms로 사라졌습니다.
- **거대한 단일 문단은 구조적 한계입니다.**
  - 1MB 한 문단: 입력 p50 205ms, Enter 1.1초.
  - ProseMirror가 문단의 인라인 자식 전체를 대조하고(`preMatch` 1.1초/35키), Blink가 문단 전체를 다시 셰이핑합니다(`InlineNode::SetTextWithOffset`, `ShapeText...`).
  - 인라인 렉싱도 여전히 비선형입니다(100KB 14ms → 1MB 595ms).
- **로딩 시 Fluent UI 포커스 라이브러리(tabster)** 가 에디터 DOM 삽입에 반응해 100~330ms를 씁니다(`DummyInputManagerCore._computeTransformOffsets`). 첫 강제 레이아웃이 이 함수에서 일어난 몫도 섞여 있어 추가 확인이 필요합니다.

### 3.8 발견한 기존 버그

1. **파서 예외로 노트가 열리지 않습니다.**
   - `"> quote\na. alpha\n> quote\na. alpha"`에서 marked의 blockquote 토크나이저가 `Cannot read properties of undefined (reading 'raw')`를 던집니다. 인용문 바로 뒤에 알파벳 번호 목록이 이어지는 경우이고, Tiptap orderedList 확장과 marked가 만나는 지점의 상류 버그입니다.
   - `openDocument`는 파싱 실패 시 `setContent`로 넘어가는데, 그것도 같은 예외를 던져 결국 `openDocument`가 예외로 끝납니다.
   - 그 결과 `resetDocState` 뒤의 `notifyActiveDoc`와 `setActiveIndex`가 실행되지 않습니다. 사용자에게는 "노트를 클릭해도 반응이 없는" 상태로 보입니다.
   - 에디터의 `documentContext`는 새 노트를 가리키는데 화면은 이전 노트여서, 붙여넣은 이미지가 다른 노트의 폴더로 들어갈 수 있습니다.
2. **표 셀 `position: relative`** 로 인한 스크롤 끊김(§3.7).

## 5. 개선 계획

원칙:
- 결과가 같음을 증명할 수 있는 수정부터 합니다.
- 큰 변화는 측정·검증 절차를 먼저 정합니다.
- 각 단계는 벤치 전후 비교, 회귀 테스트, 독립 리뷰, 커밋 분리를 거칩니다.

### 1단계 — 효과가 크고 변경이 작은 것

1. **컨테이너 블록 `content-visibility: auto`** (CSS 1줄)
   - **대상**: 최상위의 목록·표·코드블럭·인용·이미지 래퍼. 문단과 헤딩은 제외합니다(§3.4 실험 C 선택자). `contain-intrinsic-size: auto <추정 높이>`를 함께 씁니다.
   - **효과(측정됨)**: 1MB 목록·표·코드 문서의 한글 IME가 조합당 1~2초에서 5~25ms로 줄고, 입력은 5~15배, 로딩은 약 2배 빨라지며 표 스크롤 끊김도 사라집니다. 100KB에서도 회귀 없이 개선됩니다.
   - **위험**: 화면 밖 블록 높이가 추정값이라, 처음 스크롤할 때 스크롤바 크기가 바뀌고 위쪽 블록이 그려지며 위치가 움직일 수 있습니다(스크롤 앵커링이 보정).
   - **검증**: 머지 전에 아래를 모두 확인합니다(자동화 가능한 항목은 bench에 시나리오로 추가).
     - 개요 점프, 줄 이동(Ctrl+G), 찾기 다음/바꾸기의 스크롤 위치
     - 화면 밖 블록으로의 방향키 이동과 전체 선택 복사
     - 이미지·블록 드래그 앤 드롭, 표 열 크기 조절, 머메이드 미리보기
     - 포커스 모드 흐림(CSS), PDF 내보내기(복제 DOM이라 영향 없어야 함)
     - 스크롤바 안정성
2. **이미지 로딩 재설계** (메모리 2GB대 → 수백 MB 목표, 메인 스레드 base64 15초 제거)
   - **a.** data URL 대신 **Blob URL**을 씁니다. 인코딩 비용을 없애고 V8 힙 밖에 둡니다. 캐시는 경로별 참조 수를 세어, 쓰는 NodeView가 없고 캐시에서 밀려난 URL만 `revokeObjectURL`합니다. 노트 폴더 변경·롤백 시 캐시를 비우는 기존 규칙은 유지합니다.
   - **b.** **보이는 근처에서만 읽기**: 편집기별 IntersectionObserver 하나(rootMargin 1~2화면)로 NodeView의 소스 해석을 늦춥니다. `img.decoding = "async"`도 추가합니다.
   - **c.** **PDF 내보내기 보정**: 내보내기는 에디터 DOM을 복제해 `innerHTML`로 넘기므로, 복제본의 이미지를 내보내기 시점에 data URL로 바꿔 넣습니다. Blob URL과 미로딩 이미지는 headless Edge에서 보이지 않기 때문입니다.
   - **검증**: images-100k/1m 벤치(힙, 전체 표시 시간, 첫 텍스트 시간), 이미지 복사(Ctrl+C), 교체·드래그 재정렬·크기 조절, 폴더 전환 뒤 이전 폴더 이미지 누수 없음, PDF에 모든 이미지 포함.
   - **보류안**: Tauri asset 프로토콜 + 네이티브 `loading="lazy"`가 엔진에 맡기는 가장 깔끔한 방법입니다. 다만 capability 범위를 넓혀야 해 AGENTS.md의 개인정보 원칙 검토가 필요하므로 a~c 다음에 판단합니다.
3. **파서 예외에 대한 방어** (§3.8-1, 정확성)
   - `openDocument`가 예외로 끝나지 않게 합니다. 파싱이 실패하면 원문을 편집 불가 상태로 보여주고 안내를 띄워, 저장이 원문을 망가뜨리지 않게 합니다. 전환 상태(`notifyActiveDoc`, `activeIndex`, `documentContext`)도 일관되게 유지합니다.
   - 문제 입력을 회귀 테스트로 고정하고 상류(Tiptap)에 보고합니다.

### 2단계 — 중간 규모

4. **증분 마크다운 직렬화**
   - 최상위 블록별 마크다운을 (노드, 직전 형제) 키로 캐시하고 이어 붙입니다. 최상위 렌더링에서 결과에 영향을 주는 문맥은 직전 형제뿐입니다(빈 문단 뒤 빈 문단 → `&nbsp;`).
   - 자동저장·노트 전환이 O(바뀐 블록)이 되어 1MB에서 100~160ms 멈춤이 사라집니다.
   - **검증**: 코퍼스 전체와 무작위 편집에서 `editor.getMarkdown()`과 바이트 단위 동일성을 퍼징합니다. `@tiptap/markdown` 내부 API에 기대므로 업그레이드 시 재확인하도록 테스트로 고정합니다.
5. **코드블럭 NodeView 경량화**
   - 복사 버튼은 템플릿 `cloneNode`로 만들거나 호버·포커스 때 만들고, 토글·내보내기 버튼은 머메이드일 때만 만듭니다.
   - **목표**: code-1m DOM 133만 개와 로딩 시간 감소.
   - **검증**: 머메이드 승격(언어 변경), 버튼 접근성·포커스.
6. **표 셀 `position: relative` 한정**
   - 리사이즈 핸들이 있는 셀과 선택 셀에만 적용합니다(`:has(.column-resize-handle)`, `.selectedCell`).
   - 1단계 1번으로 대부분 해소되므로, 그 뒤에도 스크롤 히트테스트가 남는지 측정하고 판단합니다.
7. **거대 단일 문단의 인라인 렉싱 비선형**(100KB 14ms → 1MB 595ms)의 원인을 프로파일로 확인합니다. WikiLink 인라인 토크나이저의 `start`가 텍스트 토큰마다 `indexOf("[[")`로 남은 문단 전체를 훑는지 등을 봅니다.

### 3단계 — 구조적 한계 (지금은 수용, 기록만)

8. **문단·헤딩 수만 개짜리 초대형 문서**: 1MB에 최상위 블록 2만~4만 개면 키당 50~80ms입니다. 원인은 Chromium의 문서 전체 커밋·페인트·선택 동기화입니다. `content-visibility`를 문단까지 넓히면 내부 IntersectionObserver 비용이 더 커지고, 근본 해결은 화면 밖 블록을 DOM에서 빼는 가상화(ProseMirror 구조 변경)입니다. 실사용 1MB 노트(소설형, 블록 수천 개)는 입력 15ms 수준으로 이미 문제가 없어 보류합니다.
9. **거대 단일 문단 편집**(1MB 한 문단 입력 205ms, Enter 1.1초): ProseMirror와 Blink 모두 문단 단위로 다시 계산하는 구조라 앱 쪽 해법이 없습니다.
10. **로딩 시 tabster 비용**: 편집 영역을 tabster 관찰에서 제외할 수 있는지 확인합니다(측정 후 판단).

### 하지 않기로 한 것

- **모든 블록 `content-visibility`**: 블록 수가 많은 문서에서 역효과가 측정됐습니다(§3.4).
- **자동저장 I/O 경로 변경**(충돌 확인 읽기를 stat으로 대체 등): 1MB에서 메인 스레드 비용이 수 ms 수준입니다. 클라우드 동기화 안전장치를 건드릴 이유가 아직 없습니다.

### 6.1 10MB: 크기에 비례해 확장되는가

수정 후 코드로 10MB 3종을 1회씩 측정했습니다. 10MB 텍스트 노트는 실사용을 대표하지 않으므로, 판단이 아니라 확장성 확인 용도입니다.

| 10MB | 로딩 (1MB 대비) | 입력 p50 (1MB 대비) | 자동저장 최장 |
|---|---|---|---|
| novel-en | 3.26초 (6.0배) | 133ms (8.9배) | 123ms |
| lists | 12.9초 (9.0배) | 1,716ms (23배) | 1,293ms |
| mixed | 13.2초 (9.5배) | 1,783ms (24배) | 876ms |

- **로딩은 크기에 비례합니다.** 기존 코드는 1MB 소설이 9초였으므로, 10MB는 약 100배인 15분으로 추정됩니다(O(n²)).
- **입력 지연은 크기보다 빠르게 늘어납니다.**
  - §3.4의 엔진 비용(문서 전체 페인트·커밋·선택 동기화·IME 연동)이 남아 있다는 뜻입니다.
  - 한글 IME는 조합 갱신마다 처리 시간이 입력 간격(90ms)보다 훨씬 길어, 이벤트가 쌓여 p50이 2분(lists 122초, mixed 117초)까지 밀렸습니다. 사실상 입력이 멈춘 상태입니다.
- **같은 빌드에 1단계 1번(컨테이너 `content-visibility`)을 넣으면**:
  - lists-10m: 로딩 12.9→4.9초, 입력 1,716→166ms, Enter 2,771→283ms, IME 122초→168ms
  - mixed-10m: 로딩 13.2→8.6초, 입력 1,783→657ms, IME 117→27초
  - 다만 mixed-10m은 컨테이너 블록이 수만 개라 스크롤 p95가 172→270ms로 나빠졌습니다. 1MB에서는 나타나지 않던 현상입니다. 1단계 1번을 적용할 때 **블록 수 상한에서 선택자 범위를 조정할지** 함께 측정해야 합니다.
- **자동저장 직렬화는 10MB에서 0.9~1.3초** 멈춤이 됩니다. 2단계 4번(증분 직렬화)의 필요성이 크기에 따라 커지는 것을 보여줍니다.

## 7. 2차 작업 (브랜치 `claude/perf-phase2`)

§5의 1단계 세 항목을 처리했습니다. 각 항목은 먼저 실제 앱에서 재현·측정한 뒤 수정했고, 수정마다 독립 리뷰 에이전트의 적대적 리뷰를 거쳤습니다.

### 7.1 컨테이너 블록 화면 밖 생략 — 크기를 추정하지 않는 방식

**실험 규칙을 그대로 넣으면 안 되는 이유(측정).** `content-visibility: auto`로 건너뛴 블록의 높이는 `contain-intrinsic-size` 추정값(3em)입니다. 벤치에 `--nav`(개요 점프·줄 이동·찾기를 실제 UI로 실행하고 도착 위치를 기록)를 추가해 확인했습니다.

- 실험 C 규칙에서는 1MB 목록·표·코드 문서의 찾기와 줄 이동이 목표에서 수천~10만 px 벗어난 곳에 멈췄습니다.
- 스크롤 높이도 실제의 1/5(52만 → 9만 px)로 시작해, 스크롤할수록 늘어났습니다.

**가설 기각.**

- IME 비용이 편집 불가 요소(체크박스·코드블럭 버튼) 때문인지 확인하려고, 해당 요소를 제거하고 측정했습니다. 차이가 없었습니다.
- 비용은 편집 영역 전체의 DOM 노드 수에 비례했습니다(약 8.5µs/노드). 따라서 브라우저가 화면 밖을 건너뛰게 하는 것 외에 앱 쪽 해법이 없습니다.

**방식.** 높이를 추정하지 않습니다.

- `contain-intrinsic-size: auto`가 블록의 실제 렌더링 크기를 기억합니다.
- `OffscreenBlocks` 플러그인은 기억된 크기가 없거나 틀릴 수 있을 때만 생략 클래스를 한 프레임 떼어 전체 레이아웃(기존과 같은 비용)을 한 번 수행합니다.
  - 화면 밖 생략 대상 블록이 생기거나 바뀔 때
  - 폭이 바뀔 때
  - 웹폰트가 로드될 때
  - 글꼴·문단 간격·줄바꿈 설정이 바뀔 때
- 격리(containment)는 항상 적용합니다. 그래서 블록은 생략 여부와 관계없이 같은 크기로 측정됩니다.
- **격리의 부작용과 대응**
  - 목록 마지막 항목의 아래 여백이 목록 밖으로 나가지 못해 목록마다 4px가 늘어납니다. 여백을 목록 자체로 옮겨 상쇄했고, 이 규칙은 격리가 없어도 레이아웃이 같습니다.
  - 비동기로 높이가 바뀌는 블록(이미지, Mermaid)과, 더 큰 여백이 빠져나가는 목록(항목 끝이 구분선·헤딩·인용)은 대상에서 뺐습니다.
  - 목록 번호(`1001.`)가 잘리지 않게 `overflow-clip-margin`을 넣었습니다.
  - 편집기보다 넓은 표(약 17열 이상)는 이제 편집기 전체가 아니라 표 자체가 가로 스크롤됩니다.

**검증(기존 빌드 대비, 실제 앱).**

- `--geometry`: 코퍼스 12개와 경계 사례 문서 2개에서 모든 최상위 블록 높이가 0.1px 안에서 같았습니다.
  - 경계 사례: 1000번대 번호, 로마 숫자, 구분선·헤딩·인용으로 끝나는 목록, 20열 표, 중첩·할 일 목록.
  - 예외는 편집기보다 넓은 표 하나입니다. 건너뛰는 동안 자신의 가로 스크롤바만큼(6px) 작게 계산됩니다.
- `--nav`: 개요 점프·줄 이동·찾기의 도착 위치가 기존 빌드와 같았고, 폭이 바뀐 뒤에도 같았습니다.
- `--visual`: 블록 스크린샷의 차이는 줄 단위 1px 반올림뿐이었습니다(`pngdiff.mjs`가 판별).
- PDF 내보내기 경로(격리 해제)는 기존과 0.00px 차이입니다.

**효과.**

| 문서 | 한글 IME p50 | 입력 p50 | Enter p95 | 스크롤 p95 |
|---|---|---|---|---|
| code-100k | 88 → 7ms | 18.5 → 5.0ms | 57 → 21ms | |
| tables-100k | 45 → 5ms | | 36 → 22ms | 21 → 18ms |
| lists-1m | 966 → 6ms | 76 → 5ms | 200 → 46ms | |
| code-1m | 2,102 → 29ms | 205 → 20ms | 458 → 88ms | |
| tables-1m | 1,364 → 18ms | 126 → 19ms | 249 → 61ms | 167 → 19ms |
| mixed-1m | 872 → 85ms | 74 → 23ms | 346 → 124ms | |

- 문단·헤딩 위주 문서는 변화가 없습니다. headings에서 보인 차이는 교차 재측정으로 노이즈임을 확인했습니다.
- 로딩 시간은 그대로입니다. 첫 레이아웃을 전부 수행하기 때문이고, 실험 C의 로딩 2배 개선은 정확성을 위해 포기했습니다.

### 7.2 파서 예외 — 원인 수정

`"> quote\na. alpha\n> quote\na. alpha"`가 열리지 않던 원인은 marked의 blockquote 토크나이저에 있습니다.

- 이 토크나이저는 마지막 목록 토큰을 내장 `list` 토크나이저로 다시 읽고, 성공한다고 가정합니다.
- `a.`, `iv.` 목록은 Tiptap orderedList 확장만 읽을 수 있습니다. 그래서 내장 토크나이저가 `undefined`를 돌려주고 예외가 납니다.

수정 내용과 검증:

- `list` override가 그런 목록을 확장 토크나이저로 다시 읽습니다.
- 다른 모든 호출에서는 같은 입력을 확장이 이미 거절한 뒤에만 도달하므로 결과가 바뀌지 않습니다.
- 리뷰 에이전트가 무작위 40,000건에서 토큰 트리가 동일함을 확인했습니다. 기존에 예외를 던지던 1,816건은 모두 정상적으로 파싱됩니다.

`openDocument`가 예외로 끝나지 않게 하는 방어(원문 읽기 전용 표시)는 알려진 재현 입력이 더 이상 없어 보류했습니다. 파서 퍼즈 테스트(무작위 인용·목록 2,000건 무예외)를 회귀 테스트로 남겼습니다.

### 7.3 이미지 — 전용 스킴 `noten-asset`

- **1차 시도(Blob URL).**
  - base64 변환을 없애 전체 표시가 24.5 → 5.8초로 줄었습니다.
  - 그러나 노트의 이미지 전체(627장, 527MB)를 Blob으로 들고 있어야 해서 WebView2의 Blob 저장소 한도에 걸렸습니다. 앱 첫 로딩에서 29~62장이 깨졌고, `blob:` URL을 fetch해도 실패했습니다. 앱 코드가 해제한 것은 0건입니다.
  - 동시 읽기를 제한하는 큐로도 해결되지 않았습니다.
  - 결론적으로 이미지 바이트를 JS로 읽어 오는 방식 자체가 문제였습니다.
- **채택(사용자 결정).**
  - Obsidian(`app://`)·Joplin(`joplin-content://`)과 같은 방식입니다. `<img src>`가 복사본 파일을 가리키는 전용 스킴 주소(`noten-asset`, `convertFileSrc`)가 되고, 읽기·캐시·해제는 브라우저가 합니다.
  - 처음에는 Tauri 기본 asset 프로토콜을 썼습니다. 리뷰에서 두 가지 문제가 확인되어 전용 스킴으로 바꿨습니다.
    - 파일을 UI 스레드에서 동기로 읽습니다(tauri 2.10.3 `protocol/asset.rs`). OneDrive "필요할 때 다운로드" 파일이면 창과 모든 IPC가 멈출 수 있습니다.
    - 다이얼로그 플러그인이 실행 중에 범위를 넓힙니다.
  - 전용 스킴의 동작:
    - Rust `note_asset_response`가 파일을 blocking 워커에서 읽습니다.
    - 허용 규칙은 코드에 고정했습니다. `$HOME`·`$APPDATA`·`$APPLOCALDATA` 아래 `.assets` 폴더 안의 이미지 확장자 파일만, 실제 경로(`canonicalize`) 기준으로 허용합니다.
    - Tauri는 등록된 스킴의 오리진을 로컬로 취급해 IPC 권한을 줍니다. 그래서 모든 응답에 sandbox CSP와 nosniff를 붙여, 창이 SVG 문서로 이동해도 스크립트가 실행되지 않게 했습니다.
  - 실제 앱에서 확인한 범위:
    - 로드됨: 한글 폴더 안 `.assets`.
    - 차단됨: `.assets` 안의 비이미지, `..`로 `.assets` 밖을 가리키는 경로, 바깥을 가리키는 junction, `C:/Windows/win.ini`. 판정은 실제 경로 기준이라 `..`가 다른 `.assets` 안으로 해석되면 허용됩니다.
  - 저장 방식(`.assets/<노트ID>/<해시>` 복사본, 마크다운에는 상대 경로)은 그대로입니다.
- **PDF.** 인쇄용 headless 브라우저가 `noten-asset` 스킴을 읽지 못하므로, 내보내기 사본의 이미지를 파일에서 한 장씩 읽어 data URL로 바꿉니다. 읽지 못한 이미지는 빼고 경고로 알립니다. 실제 앱에서 60장 모두 주소 → 파일 경로 역변환과 읽기가 되는 것을 확인했습니다.
- **효과(images-1m, 627장).**
  - 전체 표시: 24.5~39.5초 → 2.7~2.9초(기본 asset 프로토콜로는 3.4초. 읽기가 병렬로 돌기 때문입니다).
  - 첫 로딩 멈춤: 없음.
  - 임시 가비지 2GB: 사라짐. GC 후 JS 힙은 원래도 25MB였습니다. 2GB는 보관량이 아니라 변환 쓰레기였습니다.
  - images-100k 전체 표시: 2.2초 → 0.5~0.6초.
  - 첫 텍스트 표시는 기존 빌드와 교차 측정했을 때 같습니다.
- **덤.** 이미지 드래그 고스트가 노드의 상대 경로(해석 불가)를 쓰던 문제도 고쳤습니다.

### 7.5 거대 단일 문단 인라인 렉싱 — 해결

- **측정**
  - 1MB 한 문단을 잘라 파싱한 시간: 100KB 35ms → 800KB 561ms. 크기가 두 배가 될 때마다 약 3배로 늘었습니다.
  - Underline을 빼면 800KB 렉싱이 515ms에서 61ms로 줄었습니다.
- **원인**
  - marked는 텍스트 토큰마다 인라인 확장의 `start` 콜백에 "문단의 남은 부분 전체"를 넘깁니다.
  - Underline(`indexOf("++")`)과 WikiLink(`indexOf("[[")`)는 해당 문자가 없는 문단을 매번 끝까지 훑습니다.
- **수정**
  - `firstIndexOf(needle)`로 만든 `start`에 한해, FastLexer가 블록 안에서 찾은 절대 위치(또는 "없음")를 기억하고, 렉싱이 그 위치를 지나야 다시 찾습니다.
  - 이것이 정확한 이유: 렉싱 중인 텍스트는 항상 블록의 접미사이고, 접미사에서의 첫 위치는 그 오프셋 이후 전체에서의 첫 위치와 같습니다.
  - WikiLink는 `firstIndexOf("[[")`를 직접 씁니다.
  - Tiptap Underline의 `start`는 "그 함수 자체일 때만" 같은 의미의 함수로 바꿉니다. 이 동등성은 테스트로 고정했습니다.
- **검증**
  - 퍼즈 1,500건에서 토큰 트리가 기억하지 않는 렉서와 같았습니다. 리뷰 에이전트도 stock marked와 4,000건을 비교했습니다.
  - 교체가 빠지면 속도 테스트가 실패합니다(변이 확인).
- **효과(앱)**
  - 1MB 한 문단 로딩: 1,359 → 858ms.
  - 1MB 한 줄 로딩: 1,354 → 838ms.
  - 나머지 문서는 교차 측정에서 변화가 없었습니다.

### 7.6 유휴 시간 직렬화 캐시 채우기

- **동작**
  - 편집이나 노트 전환 뒤 300ms가 지나면, `requestIdleCallback` 조각마다 캐시에 없는 블록을 렌더링합니다.
  - 문서가 바뀌면 처음부터 다시 돕니다.
  - 캐시 키가 (블록, 이전 블록)이라 도중에 바뀌어도 결과가 틀릴 수 없습니다.
- **효과(1MB)**
  - 첫 자동저장 최장 작업: 172 / 140 / 109 / 75ms → 0 (목록 / 표 / 혼합 / 한 문단).
  - 입력·IME·로딩은 변화 없음.
- **한계**: 쪼갤 수 없는 거대 블록 하나는 유휴 시간에 긴 작업 1회로 남습니다.
