Invariants for the Tiptap editor layer: Markdown serialization and parsing, ProseMirror plugins and decorations, wiki/anchor links, images, tables and Mermaid, and the off-screen block skipping that keeps typing cheap in large notes.

## Editor and Markdown

- The Markdown string is the serialization format and single source of truth on disk. A single persistent Tiptap v3 instance with `@tiptap/markdown` provides WYSIWYM editing, and stays readonly until the first document loads.
- Use the official `@tiptap/markdown` API only: `editor.getMarkdown()`, `editor.commands.setContent(value, { contentType: "markdown" })`, and `contentType: "markdown"` at init. Do not use community-package APIs such as `editor.storage.markdown.getMarkdown()`. Import menus from `@tiptap/react/menus` and `Markdown` from `@tiptap/markdown` — v3 paths, not v2 examples.
- Markdown is cached in `useMarkdownState.markdownRef` (`getCachedMarkdown` / `primeMarkdown`). Tiptap's `onUpdate` marks the cache stale; `scheduleAutoSave`'s `createSnapshot` refreshes it. Any imperative content load must call `primeMarkdown(md)` — `resetDocState` does this centrally.
- `TiptapEditorHandle.openDocument({ noteId, filePath, markdown, reason })` is the normal load/switch path; it restores a cached per-document ProseMirror `EditorState` when the Markdown signature still matches, keeping at most 20 sessions for selection and undo history. A session keeps the signature of the Markdown it was loaded from for as long as its doc is the same object (`src/utils/documentSession.ts`), because a note parsed from non-canonical Markdown (legacy `&nbsp;` cells, hand-aligned tables) does not serialize back to its file; signing only the serialized form would reject the cache on every switch until the note is rewritten. `setContent(md)` is the fallback wrapper. Call `invalidateDocumentSession(noteId, filePath)` before a deleted or identity-invalid session could be reused.
- The `Markdown` extension must stay configured with `createFastMarked()` from `src/extensions/fastMarkdownLexer.ts`. Stock marked's inline lexer is O(n²) on a single large block dense with code spans, links, HTML, or escapes — a multi-million-char note on one line froze the app for minutes. `FastLexer` builds the inline mask in one linear pass and its output is byte-identical, so do not revert to the bare extension. `fastMarkdownLexer.test.ts` fuzzes token-tree equivalence against stock marked; when a marked upgrade reshapes `Lexer.inlineTokens`, re-transcribe only the main tokenization loop. `createFastMarked()` also wraps the block tokenizers Tiptap registers (`boundedBlockTokenizers.ts`): `taskList`, `orderedList` and `table` each began by splitting the entire remaining document, which made parsing O(blocks × length) — 8.7 s of a 9.4 s load for a 1 MiB note. Each wrapper hands its tokenizer a prefix ending at a line the original is proven to stop at, so the token it returns, `raw` included, is unchanged; the cut rules are argued in that file's comments and fuzzed for equivalence (the `orderedList` bound runs Noten's transcription's own line walk over a doubling window instead, and is not exact for the stock tokenizer), and a Tiptap upgrade that changes one of those tokenizers needs its rule re-checked. Inline `start` callbacks built with `firstIndexOf(needle)` are remembered per block instead of rescanning the paragraph for every text token. Finally, a blockquote ending in an `a.`/`iv.` list re-lexes it through marked's built-in `list` tokenizer, which cannot read those markers and made the note fail to open; the instance falls back to Tiptap's `orderedList` tokenizer there. The instance also closes a fence as CommonMark does, only at the opening fence's own character (`commonMarkFence`): marked 17 accepts the fence followed by any mix of backticks and tildes, so a code line such as ```` ```~~~ ```` or `~~~```` ended the block, was dropped, and the code after it read as Markdown on the next save, at the top level, in list items and in quotes. It takes over only when marked's match ended at such a line, and builds the token as marked's `fences` tokenizer does, so every other fence lexes exactly as before; `fastMarkdownLexer.test.ts` fuzzes that against stock marked. `orderedListTokenizer.ts` tracks fences with the same closer. A fence that such a line no longer closes, and nothing later closes, runs to the end of the note (or of its item or quote), as CommonMark and GitHub read it: the Markdown after it becomes code, kept whole and saved inside a longer fence (`renderCodeBlockMarkdown`), and the fence-length rule is what makes that save stable.
- HTML in Markdown is parsed with a schema built once per manager (`markdownHtmlSchema.ts`, installed by importing `fastMarkdownLexer.ts`). The stock `parseHTMLToken` calls `generateJSON`, which rebuilds the whole schema for every HTML token, and every sized image is saved as `<img>` HTML: a note with 200 of them spent ~190 ms loading in Chromium (and a paragraph of 2,000 inline images 1.5 s) where the cached schema takes ~23 ms (102 ms). Only the schema step differs, so the JSON is identical. The method is transcribed from `@tiptap/markdown`, and `markdownHtmlSchema.test.ts` compares it with the stock one on every kind of HTML token and on the Markdown fixtures, so re-transcribe it when an upgrade makes that test fail. Test timings under jsdom stay higher, because jsdom sets up a selector engine for every parsed document and never releases its listeners; WebView2 has neither cost.
- `editor.getMarkdown()` is replaced by the incremental serializer in `IncrementalMarkdown.ts`: each top-level block's Markdown is cached against the pair (block node, previous block node), so autosave, note switches and export re-render only the blocks a change touched (1 MB cost 80-130 ms per pause in typing before). The result must stay byte-identical to the stock serializer, which `IncrementalMarkdown.test.ts` fuzzes. It relies on `@tiptap/markdown` internals — the document renderer joining children with `"\n\n"`, and a top-level renderer reading nothing but its node and `previousNode` — so re-check both on every upgrade. Install it in `onBeforeCreate`; Tiptap v3 emits `onCreate` asynchronously, so anything hooked there misses the first call. After an edit settles, a `requestIdleCallback` pass fills the cache for blocks other than the one being edited; a block that throws there is left to the save that reports it.
- Inline code is fenced by `CodeSpanFence.ts`: one backtick more than the content's longest backtick run, with a space inside each side when the content starts or ends with a backtick (or starts and ends with a space around other text). The stock code mark always emitted one backtick, so `` a`b `` came back as code `a` plus stray text. `@tiptap/markdown` renders a mark only around a placeholder and hands it nothing but the mark's attrs, so `CodeSpanFence` wraps the manager's `renderNodes` to annotate each code run's mark with its fence, and `NotenCode` renders from those attrs. Keep `CodeSpanFence` after `Markdown` (the manager is created in its `onBeforeCreate`), keep `NotenStarterKit` in place of `StarterKit` (it swaps `NotenCode` in for the stock code mark), and leave single-backtick runs unannotated so their output stays byte-identical to the stock serializer. It relies on marks reaching the serializer only through `renderNodes` and on the mark's attrs reaching its renderer, so re-check both on a `@tiptap/markdown` upgrade.
- The code mark must rank last among marks. The serializer nests a node's marks by schema rank, lowest outermost, and the stock rank (right after bold) put italic, strike, underline and wiki links inside the backticks: `` *`a`* `` saved as `` `*a*` ``, whose asterisks read back as code text. `NotenCode` takes priority 99, one below the default, so it ranks after every mark wherever it is listed; the DOM nests the same way (`<em><code>`), and no editor CSS selector depends on the order. The lower priority also runs its plugins (the `Mod-e` shortcut, the exit-on-`ArrowRight` keymap, input and paste rules) after default-priority extensions. Do not raise it back to the default or add a mark below it.
- Clipboard `text/plain` goes through `sliceToPlainText` (`src/utils/clipboardText.ts`), joining block boundaries and hard breaks with a single `\n` so pasted text matches the on-screen line count. Only `text/plain` is overridden — `text/html` stays with ProseMirror, so rich targets keep formatting and in-app paste round-trips via `data-pm-slice`.

## Editor Decorations

Per-keystroke work in the editor must be incremental — no plugin or observer may re-derive whole-document state on every transaction:

- Focus mode (`FocusMode.ts`): per-selection cost is constant regardless of document size. The plugin never walks the document (no `doc.descendants` on any path); the current block's boundaries come from the resolved selection head (`$head.before(1)` / `$head.after(1)`). The decoration set holds at most one node decoration; same-block caret moves return the previous plugin state by reference, and same-block edits remap through `tr.mapping`. Dimming every other block is pure CSS. The active flag lives in extension storage so it survives `view.updateState()` note swaps, which emit no transaction.
- In-editor find (`SearchHighlight.ts`): `findSearchMatches` is the single match finder shared by `SearchBar` and the plugin. The full match list backs the counter, next/prev, and replace-all, but only `SEARCH_DECORATION_CAP` (2000) decorations are drawn — `selectMatchesToDecorate` picks those nearest the visible range, fed by a scroll-driven plugin `view`. Keep the count truthful and the drawn set bounded; do not decorate every match.
- Code-block highlighting (`incrementalLowlight.ts`): `MermaidCodeBlock` filters the stock lowlight plugin out of its inherited plugins (`isStockLowlightPlugin`, matched on the plugin key `lowlight$…`) and installs an incremental one in its place — the stock plugin walks the whole document on every transaction and re-highlights every code block whenever the selection sits in one (3.3 s per key in a 1 MiB note). Changed blocks are found by node identity and checked against the mapping, and each block's highlight is cached per immutable node. The filter is pinned by a test asserting no stock plugin survives; if a `@tiptap/extension-code-block-lowlight` upgrade renames its key, fix the matcher rather than letting both highlighters run.
- Wiki-link "missing link" decorations (`WikiLink.ts`): a target's existence changes only via the forced refresh meta (`refreshWikiLinkDecorations`, dispatched from `App.tsx` when the docs/title set or locale changes), so a plain edit remaps the existing `DecorationSet` and recomputes only the changed range. `findDocByTitle` is O(1) via a title map cached per `docs` array reference.
- Anchor links (`AnchorLink.ts` + `src/utils/headingSlug.ts`): a link mark whose href starts with `#` jumps through the same `handleOutlineJump` path the outline panel uses. Fragment resolution walks the document only at click time and once per link-popover session for `#` autocomplete — never per transaction. The popover stores GitHub-style slugs (`#서론-개요`) so serialized destinations never contain spaces, but `resolveHeadingFragment` stays tolerant of raw titles and percent-encoding — on-disk markdown is never rewritten to conform.

## Off-screen Blocks

Chromium's per-keystroke and per-IME-composition cost grows with the whole contenteditable, so DOM-heavy top-level blocks (lists, code blocks, tables) are skipped off screen with `content-visibility: auto` (`OffscreenBlocks.ts` + the "Off-screen skipping" CSS in `tiptap-editor.css`).

- Paragraphs and headings are skipped too, but only while the note has at most `MAX_TEXT_SKIP_BLOCKS` top-level blocks (the plugin's second root class, `noten-skip-offscreen-text`). Every IME composition update counts characters from the start of the editor to the caret, and Chromium's text iterator does not enter a skipped block, so unskipped prose made Hangul cost grow with the text before the caret (61 ms per update at the end of a 1.1M-character note, 17 ms with prose skipped). Every skipped element also costs the browser per frame, and re-enabling skipping after a measuring frame grows steeply with their count, so past the limit (20,000 paragraphs: typing and scrolling slower, seconds per re-measure) prose keeps its normal layout until the note is `TEXT_SKIP_HYSTERESIS` blocks back under it — its containment rides on the same class, so crossing either way re-measures, and the gap keeps Enter/Backspace at the limit from re-measuring on every key. Opening a note through `openDocument`'s `view.updateState` path builds a new plugin view, which starts from the plain limit; the `setContent` fallback keeps the current one. Below the limit the price is a few ms of typing latency (p50 and p95) and scroll frames. A test pins `SKIPPABLE_BLOCK` / `SKIPPABLE_TEXT` to the stylesheet's selectors. Keep the CSS selector and `SKIPPABLE_TEXT` identical.
- Skipped sizes are never guessed: `contain-intrinsic-size: auto` remembers each block's rendered size, and the plugin drops its root class for a frame (a full layout) whenever sizes could be missing or stale — an off-screen skippable block created or changed (except the block holding the caret when the update scrolls to it and the editor has focus, so the scroll happens: plugin views run before ProseMirror's scroll, so Enter on the last visible line would otherwise re-measure the whole note), a width change, a web-font load, or a typography setting (`remeasure()`). A new layout input that changes block heights must call `editor.storage.offscreenBlocks.remeasure()`, or jumps, find and the scrollbar land off target.
- The containment is applied permanently (not only while skipped), so a block measures the same either way. It stops a list's last-item margins from collapsing out of the list; the list margin rules next to it compensate exactly and are layout-neutral without containment. Blocks whose content changes height asynchronously (images, Mermaid) or holds larger escaping margins (rule, heading, quote in a list) are excluded and keep today's layout. Keep the CSS selector and `SKIPPABLE_BLOCK` identical.
- Check layout changes here with `node bench/run.mjs --geometry` against the previous build and `--nav` (see `bench/README.md`).

## Wiki Links and Titles

`[[Title]]` names its target by title alone, so duplicated titles need one agreed resolution rule, shared by every consumer:

- `findDocByTitle` orders candidates by `createdAt` ascending with the note id as tiebreaker — never by position in `docs`, which is the sidebar sort order (under the default `updated-desc`, editing one of two same-titled notes would otherwise silently re-point every link at it).
- When the link's own note is in a group, a candidate in that same group wins. `findDocsByTitle` exposes the full candidate list for ambiguity checks.
- The click handler resolves the target and hands `navigateToDoc` an **id**. Do not re-resolve a title on the App side; two lookups can disagree.
- `renameNote` skips back-link rewriting entirely when the OLD title was shared by another note: `[[Old]]` cannot be attributed to one target, and rewriting would re-point links belonging to the other note. It returns `RenameNoteResult.linkRewriteSkipped` and App.tsx surfaces the transient notice.
- `normalizeNoteTitle` (`src/utils/noteText.ts`) is the single definition of "same title" for link resolution, duplicate detection, and rename.
- `customName` on a document means the user manually renamed it; auto-title derivation is permanently disabled for that document.

## Images

- Image sources are note-local relative asset paths (`.assets/<noteId>/<hash>.<ext>`) on insert, replace, drop, and paste. Legacy base64 is still accepted (`allowBase64: true`) and migrated on startup once per notes directory.
- Image NodeViews share one per-editor `transaction` subscription (`registerImageSelectionSync` in `ImageView.ts`) that re-syncs selection outlines only when the node-selected position or readonly flag changes. Do not re-add a per-NodeView `editor.on("transaction")` listener — that made selection bookkeeping O(images) on every keystroke.
- Editor images load their `.assets/` file through the app's `noten-asset` URI scheme (`resolveRenderableImageSource` → `convertFileSrc(path, "noten-asset")`), the way Obsidian's `app://` or Joplin's `joplin-content://` do: the browser reads, caches and evicts the image itself. Do not go back to reading assets into JS — base64 data URLs cost ~15 s of main thread for a 600-image note, and Blob URLs hit WebView2's Blob storage limit and left images broken. The scheme is served by `note_asset_response` in `src-tauri/src/lib.rs` on a blocking worker, not by Tauri's built-in asset protocol, which reads on the UI thread (an OneDrive file still downloading would freeze the window and all IPC). Build paths with `/`. The headless PDF renderer cannot load the scheme, so PDF export points those images at their files as `file:` URLs (`pointAssetImagesAtFiles`, `fileUrlForPath`); it prints the export HTML from a `file:` page and loads them itself. Do not inline them as data URLs again: the HTML then holds every image at once, and a note with ~500 MB of images passed the JS string limit and printed a blank page. Which file an image may point at is decided by the Rust command `note_image_files`, which applies `is_servable_note_image` to canonical paths, so the PDF can never show a file the editor would refuse. Edge still decodes every image in one renderer: a note with ~500 MB of images needs ~10 GB and fails with an explanation (`failure_reason`); a 60-image note (48 MB) exports in ~12 s and a 300-image one (240 MB) in ~65 s.
- Image Markdown serialization must use `serializeImageMarkdown` so `src`, `alt`, and `title` are escaped correctly for their Markdown/HTML context. When `width`/`height` are set, `renderMarkdown` emits `<img>` HTML to preserve dimensions through round-trips.
- `NotenImage` (`NotenImage.ts`) is the single Markdown config for images; the editor extends it only with its NodeView, and the Markdown tests use it as is. Importing it patches `MarkdownManager.prototype.toInlineContent` to keep image nodes. Since Tiptap 3.30, `@tiptap/markdown` parses inline HTML with the schema and keeps only its inline nodes, and Image is a block node, so a sized image inside a table row (always inline HTML there), between words, or wrapped in `<a>`/`<span>` parsed to nothing and the next save deleted it. The patch is on the prototype because the Markdown extension parses initial content inside its own `onBeforeCreate`, before any later extension can reach the instance. Do not replace it with an inline `<img>` tokenizer: it cannot see tags inside inline HTML pairs, which the manager re-joins from raw text and re-parses, and a hand-written tag grammar diverges from what the browser reads. `NotenImage.test.ts` and the table fixture in `markdownRoundTrip.fixtures.test.ts` fail if such an image is lost; run both on every `@tiptap/markdown` upgrade.
- On insert, images are capped to 560px width via `clampImageDimensions`. Height is always `auto` in CSS — only width is set in px, to prevent aspect-ratio distortion on narrow viewports.
- `createImageNodeView` owns resize handles, drag reorder (6px `pointerdown` threshold → `startReorder()`, single undo step), context menu, and asset-source rendering. Ctrl+C on a selected image copies the image blob, not HTML.

## Ordered Lists

- `NotenOrderedList` (`NotenOrderedList.ts`) replaces the stock ordered list through `NotenStarterKit`. The marker style is the stock `type` attribute (`a`, `A`, `i`, `I`, null for numbers), which `@tiptap/extension-list` already reads from and writes to Markdown (`a.`, `iv.`); Noten adds the display, the `setOrderedListStyle` command (toolbar chevron, `/` letter and roman lists) and a `a. `/`B. `/`i. ` input rule. The command restyles a selected list node, else the innermost list around the selection (at `$from`, so a selected image or table in a list counts; `selectedOrderedListStyle` reads the same list for the toolbar), converting a bullet or task list in place, and outside a list wraps the selection with the style already set, joining only a neighbouring list of the same style. It does not go through `toggleOrderedList`, which joins a new list into an adjacent numbered one before any style is set and lifts a nested task list into the numbered list around it, so the style landed on a list the user had not chosen.
- An ordered list shows the markers its Markdown holds. `renderHTML` adds `data-list-style` and the stylesheet styles that, not `ol[type]`: HTML matches `type` case-insensitively in selectors, so `[type="a"]` also matches `A`. Nesting does not restyle a numbered list; it once showed nested `1.` lists as letters. `src/styles/tiptap-editor.test.ts` checks the computed marker of each style.
- `NotenListItem` (`NotenListItem.ts`, swapped in through `NotenStarterKit`) writes the stock list-item markers, except that a letter list's items past `zz.` (702) are numbered (`listItemMarker`): Tiptap has no letter marker there and wrote `undefineda.`, which reads back as text of item 702. A toolbar restyle of a long list, or a token past `MAX_LIST_SEGMENTS` (10,000 segments, which falls back to one list in the first item's style), reaches it. It keeps the items but not the rule above: until the note is reloaded the stylesheet draws item 703 as `aaa.` while the file says `703.`, the reload splits the list in two (so the next save adds a blank line, stable from then on), and a letter list whose start is past 702 is saved all numbered and loses its style. Likewise `lower-roman` is drawn as decimal from 4000, where the file keeps `mmmm.`. Positions below 1 are written as numbers too, and `start` is read from HTML as at least 1.
- Plain-text paste of a list is decided by `MarkdownPaste` (`TiptapEditor.tsx`), not by the stock ordered-list paste plugin: Tiptap collects plugins from the extension list reversed before sorting by priority, so among equal priorities the later extension's plugin runs first, and `MarkdownPaste` handles nearly every plain-text paste. A test of paste behaviour must include `MarkdownPaste`; an editor without it exercises a path the app never takes.
- Two corrections to the stock reading, both of which rewrote the user's markers on the next save: a single ambiguous first letter (`c.`, `d.`, `l.`, `m.`, `v.`, `x.`) is a letter, not a roman numeral, unless the second item reads as roman, its roman successor (`alphaAttrsForAmbiguousMarkers`: `v.` `w.` letters, `v.` `vi.` roman); and an item whose marker kind differs from the list's first item (numbers, lowercase, uppercase, as `detectMarkerType` reads them), or whose letter style does (a roman numeral that is not a letter list's next letter; in a roman list, a non-roman letter or a single letter that is not its next numeral), starts a new list (`listSegmentStarts`), since the serializer writes adjacent lists a blank line apart (a single newline inside a list item) and the stock tokenizer merged them back into one. So `a.` `b.` then `i.` is two lists, while `h.` `i.` `j.` stays one. The split is made in `parseMarkdown`, over the items of the token the stock tokenizer returned, at every nesting level: splitting in the tokenizer instead covered only the top level, and each short list it returned made the bounded tokenizer rescan the rest of the run, quadratic in a long run of alternating markers. Re-check both against `@tiptap/extension-list` on an upgrade.

- `NotenOrderedList`'s Markdown tokenizer is the stock one transcribed in `orderedListTokenizer.ts` with two changes to how an item's block content is dedented: each line under the item goes to the item's content column (marker, delimiter and 1-4 spaces, as CommonMark and the listItem serializer have it), and the block is then dedented by the indent its lines share (`dedentBlock`) instead of trimming its first line alone. The stock one stopped a column short and trimmed only the first line, so block content reached the lexer with its first line one column left of the rest: a task list under `1.` read its second item as the first one's text (the checkbox was lost, `\[x\] task2` was saved and drifted right on each save), a fence that was not the item's first block was dropped with its code, a character after a task list was deleted, and every code line and every paragraph after the first gained a space per save. The column alone does not cover hand-written nesting deeper than the column (`1.` then 4 spaces), and the shared dedent alone does not cover a block holding an unindented lazy line; the tests pin both. A third change reads the marker line: the stock `splitItemContent` always made the text after the marker a paragraph, so `1. - [ ] t1` lost its checkbox (saved as `1. - \[ \] t1`), `1. > q` was saved as `1. &gt; q`, and a fence there became a paragraph holding its first code line. Text there that opens a bullet or task list, a heading, a fence, a quote or a thematic break now starts the item's block content, as marked reads a bullet item's first line; an ordered marker stays text, as Tiptap keeps `- 1. a` for a bullet item. The same kinds of fault outside ordered lists are fixed in `taskListTokenizer.ts` (Task Lists) and `codeBlockMarkdown.ts` (Tables, Code Blocks and Mermaid). A fourth change reads fences: the stock loop took every line shaped like an ordered marker as a new item, inside a fenced code block too, so under `1. n` a fence holding the line `   2. x` lost that line to a nested item, and its closing fence opened a second, empty code block. A fence opened in the item's own content (0-3 columns past its content column, the marker line included, by marked's `fences` rule, which is what lexes the item's content) now keeps a marker-shaped line at or past the content column as code, measured in columns with a tab running to the next multiple of 4 (Obsidian indents with tabs). A marker-shaped line left of the column is still a new item, as CommonMark reads it. Where the fence closes follows marked: every content line reaches it dedented to the item's column, so a closing fence 1-2 spaces in (or after a tab) closes it; judged by its raw indent, it opened a second fence and the item's later code moved between items on every save. An unclosed fence runs to the end of the item, as marked reads it. A fence after bullet markers (a bullet nested in the item) holds the lines at that bullet's content column instead, and a line left of that column ends the bullet and its fence; a nested ordered item tracks its own fences, and a quote's lines never look like markers. The closing rule is the lexer's, CommonMark's same-character one (see `commonMarkFence` above); the two must agree, or the item splits where the lexer does not. A fifth change keeps every item: the stock structure kept only items at exactly a group's smallest indent, so an item less indented than its group's first (` 1. a` / `2. b`, or `      2. b` / `   3. c` under `1. a`, where the first is dropped) was consumed but never parsed and vanished on the first save. A group's base is now its first item's indent, and an item at or left of it is a sibling: CommonMark's reading of a later top-level item indented 0-3 spaces. A nested item keeps the stock rule (deeper than its group's base nests), where CommonMark goes by the parent's content column, so under `1. a` / `   2. b` / `      3. c`, `    4. d` is a sibling of `c` here and of `b` in CommonMark; every item is kept either way. the fuzz checks that every item line the list takes is an item of its token. `NotenOrderedList`'s marker reader skips `\s` as the tokenizer does, or an item indented with a no-break space had no marker and a `1.` after it was saved as a letter. It keeps the stock name, so `boundedBlockTokenizers.ts` still bounds it. Without a fence the lines each list takes are unchanged except at a marker it cannot read and at an unindented quote line (below), which `orderedListTokenizer.test.ts` fuzzes against the stock tokenizer together with exact token equality where no line is indented content, no marker line holds a block and the stock tokenizer dropped no item. The bound runs the tokenizer's own walk, so it needs no rule of its own; `boundedBlockTokenizers.test.ts`'s fuzz draws fenced lines. Re-transcribe it on an `@tiptap/extension-list` upgrade, or drop it once upstream dedents correctly.
- A line is an item only when `detectMarkerType` can read its marker: digits, a roman numeral, or one or two letters of one case (`isOrderedItemLine`). The stock pattern also takes any run of roman letters (`Vim`, `IIII`, `Civil`) and any letter pair (`Dr`, `Mr`, `St`, `No`), reads the ones that are neither as item 1, and drops the marker, so a paragraph opening with such a word lost it on the next save (`Dr. Smith said` became `1. Smith said`, and after a list `Dr. x` joined it as its next item). Such a line is now text, as in CommonMark: a paragraph, a lazy continuation line, or an item's continuation. Words that do read as markers (`im.`, `OK.`, `MIX.`) are still items; `listSegmentStarts` decides whether they join the list above. Plain-text paste needs no change, since `parsePlainTextOrderedListPaste` already rejects such markers. `boundedBlockTokenizers.ts`'s ordered-list bound reads lines by this tokenizer's rules, so it is exact for this tokenizer and no longer for the stock one: with the stock pattern, a run of `Dr.` paragraphs handed the tokenizer the rest of the run at each one, quadratic in its length (20,000 took 93 s). Its equivalence fuzz leaves such lines out of the stock kit's runs.
- An unindented `>` line ends an ordered item instead of continuing its paragraph lazily, as a block quote interrupts a paragraph in CommonMark (`interruptsLazyContinuation`), except where the item holds it: inside a fence open in the item it is code (`>>> print(1)`, a `>>>>>>>` conflict marker), and right after a quote line of the item it continues that quote. These exceptions keep the reading Noten had before the rule, not CommonMark's: CommonMark ends the item at such a line, since fenced code and quotes have no lazy continuation, but that emptied an item's fence and spilled the rest of the note into a new one. The bound in `boundedBlockTokenizers.ts` cannot see that state from outside the walk, so it runs the walk itself (`orderedListLineCount`) over a span of lines that doubles until the walk stops inside it, at least 32 lines and less than four times the lines the list takes; a guess that made no quote cut once any fence had been seen made every list in a run of `1. ```` / `   ```` / `> q` blocks split the rest of the document again (8,000 took 42 s). The stock interrupters left the quote out, so an item took it and every line after it into its block content; there marked's blockquote re-lexed its list through the `list` fallback in `createFastMarked`, back into this tokenizer, which took the rest again. `> a. x` / `foo y` repeated nested one blockquote > list > item deeper per repetition at load, was saved that deep, and past a few hundred repetitions overflowed the stack, so the note did not open (after the unreadable-marker rule above, `Dr. y` lines did the same). Such a quote now holds one list per `>` run, written apart and joined into one list on the next load, as a quote of `1.` items going through marked's own list tokenizer always has been. The rule is visible in hand-written notes: in `1. Step one` / `> Note` / `2. Step two`, the quote now follows the list, and since marked ends a quote's paragraph only at `1.` or a bullet, `2. Step two` and later items are read inside the quote (CommonMark keeps them there too, as lazy text of the quote's paragraph; marked makes them a list); before, the quote sat in item 1 and the list went on. It also costs time: marked's blockquote re-lexes a trailing list with the whole rest of the quote joined on, once per `>` run that ends in one, so `a. x` / `> q` alternating, linear before this rule (about 1 s to open at 16,000 repetitions), now takes about 12 s, and `> a. x` / `foo y`, which overflowed before, about 20 s, as `> 1. x` / `foo y` always has. The bounded fuzz leaves unindented quote lines and fence lines out of the stock kit's runs, since the stock tokenizer reads on through the one and reads marker-shaped lines in the other as items.
- One ordered list token nests at most `MAX_ORDERED_LIST_DEPTH` (100) levels; deeper items are siblings at the deepest level, so their text stays and the saved list reads back the same. Any deeper indent nests, so a list indented one more space per item nested once per item, and Tiptap parses nested lists recursively (`NotenOrderedList.parseMarkdown` → the stock one → `parseChildren` → ...): past a few hundred levels (about 300 on a cold start, more once the JIT is warm) the parse overflowed the stack and the note did not open. A nested list token's `raw` is a slice of the tokenizer's `src` (`srcStart`/`srcEnd` on each item), not its items' lines joined, which copied every deeper line once per level: a 1,500-level staircase held gigabytes of strings and ran out of memory before the parse. Ordered nesting through bullet or task items stays in one token and under the cap. Bullet lists (marked's tokenizer), task lists and quotes nested past a few hundred levels (quotes about twice as deep) still overflow the same parse, as does ordered nesting through quotes. Nesting added in the editor past the cap (Tab at level 100) is flattened back to level 100 on the next load; its text stays.

- A block on an item's marker line (a task list, quote, fence or nested list, which the stock bullet reading already produces and the ordered one now does) is handled by `NotenListItem` (`NotenListItem.ts`, swapped in by `NotenStarterKit`, for bullet and ordered items alike). The schema's `paragraph block*` has no room for it as the first child, so `normalizeListItemContent` gives such an item an empty first paragraph and wraps any bare text node (a marked `text` token after the block, which also cost the blank line before it on save) in a paragraph. The stock parse left both invalid; ProseMirror does not check content on load, but it does on edits, so Enter, Backspace or a deletion in the item and Tab on the next one threw. `NotenOrderedList.parseMarkdown` applies it too, because the stock ordered list builds its items itself instead of through the listItem extension. The editor shows the empty paragraph as an empty first line in the item. The stock listItem renderer writes the first child after the marker and indents only the children after it; a paragraph's later lines read back as lazy continuations, but no other block's do, so `1. - [ ] t1` / `   - [x] t2` was saved as `1. - [ ] t1` / `- [x] t2`, which reloaded as a second list after the item (and escaped on the next save), and a fence's code lines ended the item. `renderListItemMarkdown` writes an empty first paragraph followed by a block (or a block first, from HTML or older JSON) as that block on the marker line when the next load reads it back from there (`MARKER_LINE_BLOCKS` and `MARKER_LINE_HEAD`: a bullet or task list, quote, heading or fence whose first line still opens it, and a rule in an ordered item only), so the Markdown round-trips. Any other block stays on the lines below an empty marker line, as the stock renderer writes it: an ordered list on the marker line reads back as text (`1. 1. b`; Tab under an empty numbered item makes exactly that shape), and `- ---` is a rule of its own. An empty bullet item followed by a block (`- ` / `  ---`) still does not round-trip, as it did not before, because marked reads `- ` alone as text. The renderer indents the block's later lines exactly as the later children are, through a transcription of `renderNestedMarkdownContent` that renders each child once, and leaves paragraph-first items to the stock renderer byte for byte, which `NotenListItem.test.ts` compares. Do not render the first child a second time beside the stock renderer's pass: at every level of `- - - a` nesting that doubles, 2^depth in all. Re-check it against `renderNestedMarkdownContent` in `@tiptap/core` on an upgrade.

## Task Lists

- `NotenTaskList` (`NotenTaskList.ts`) replaces the stock task list in the editor. Its Markdown tokenizer is the stock one with `parseIndentedBlocks` from `@tiptap/core` transcribed into it (`taskListTokenizer.ts`), changing which lines under an item are its content and how they are dedented. The stock one took every line indented past the marker as content and sliced a fixed 2 columns from each, so a shallower line lost real characters (`- [ ] t1` / ` x` saved without the x, ` after` after a blank line saved as `fter`) and a sibling item CommonMark reads at 1 space became the previous item's text (` - [x] t2` saved as `\[x\] t2`). Now, against the item's content column (marker and 1-4 spaces, 2 for `- `), with indentation measured in columns and a tab running to the next multiple of 4 (counted as one column, Obsidian's tab-indented nesting was saved flat): a line at or past the column is content, dedented by it as before; a line short of it ends the item when it starts a task item (the next item of the list), a bullet, a heading, a fence, a quote or a thematic break, and is otherwise a lazy continuation, dedented by its own indent; after a blank line, a line short of it ends the list. Every line at column 0 that is not a task item still ends the list, which is the cut rule in `boundedBlockTokenizers.ts`; `boundedBlockTokenizers.test.ts` fuzzes this tokenizer bounded against unbounded, and `taskListTokenizer.test.ts` fuzzes it for exact equality with the stock one where no line falls short of the column and for kept words everywhere else. It keeps the stock name, so the bounding still applies. Re-transcribe it on an `@tiptap/extension-list` or `@tiptap/core` upgrade, or drop it once upstream dedents by the content column.
- `createNotenTaskItem` also wraps a bare text node among a task item's blocks in a paragraph (`parseTaskItemMarkdown`, through `normalizeListItemContent`). marked lexes a list item's content outside its top level, where a paragraph is a `text` token, so a task list nested in a bullet item (`- a` / `  - [x] b` / `    c`) put `c` in the task item as bare text: the schema does not allow it, edits there could throw, and a blank line before it was lost on save.
- TaskItem (since Tiptap 3.31) writes each checkbox's accessible name into both its `aria-label` and a visually hidden span in its label, on creation and on every update of the item and of each task item above it. Tiptap's default name is `node.textContent`, the item's whole subtree, so every ancestor's span held all of its descendants' text: laid out in Chromium, 1 MiB list notes took up to 1.7x as long to lay out and a keystroke deep in a large nested list cost hundreds of milliseconds.
- `createNotenTaskItem` (`NotenTaskItem.ts`) names the checkbox after the item's own first paragraph through `task.checkbox` / `task.checkboxEmpty`, so an update costs one paragraph and the name follows the locale. Never return an empty name: Tiptap falls back to its subtree default on a falsy one.
- `tiptap-editor.css` keeps the span `display: none`; screen readers name the checkbox from `aria-label` alone, as they did before 3.31, and the text leaves Chromium's IME text walk. `src/styles/tiptap-editor.test.ts` judges the rule by computed style with the real stylesheet, so a lost rule or an inline `display` from a Tiptap upgrade fails it.

## Tables, Code Blocks and Mermaid

- Tables use Tiptap v3 table extensions through `NotenTable` (`NotenTable.ts`) with `lastColumnResizable: false`, so dragging an inner column redistributes width instead of growing the table past the editor width.
- Older serializers wrote an empty table cell as a literal `&nbsp;`. `NotenTable` empties such cells in `parseMarkdown`, on lexer tokens, so fenced code and inline-code `&nbsp;` are never touched; a cell whose text only contains the entity keeps it. Do not reintroduce a string-level pass over the Markdown: it cannot see block structure. The save path relies on the serializer never emitting the placeholder, which `markdownRoundTrip.fixtures.test.ts` pins.
- A table cell's Markdown must escape every unescaped `|` as `\|`, inside code spans and links as well as plain text. GFM splits a row on each `|` not behind a backslash before any inline parsing, so a code span offers no protection; Tiptap's own tokenizer does treat code spans as atomic, which is why a Noten-only round-trip passes while GitHub shows a broken table. `NotenTable` wraps `renderTableToMarkdown`'s `renderChildren` with `escapeCellPipes`; that relies on the renderer reaching cell content only through `renderChildren`, so re-check it on a `@tiptap/extension-table` upgrade. Table tests assert the cells through the GFM row split (`gfmRowCells` in `markdownRoundTrip.fixtures.test.ts`), not only a reload. A literal `\|` inside a code span has no GFM spelling and reads back as `|`.
- `TableNodeSelect.ts` selects a whole neighbouring table on an arrow key only at the textblock's edge in that direction: `parentOffset` at the end/start for ArrowRight/ArrowLeft, `view.endOfTextblock("down" / "up")` for ArrowDown/ArrowUp (layout-bound, so its tests stub it). Anywhere else it returns false and the caret moves; it once took every arrow press in the paragraph next to a table. At the end, an exitable mark under the caret (inline code, a link) gets the first ArrowRight to step out, since `NotenCode`'s exit keymap runs after this plugin. prosemirror-tables turns the table NodeSelection into a CellSelection over every cell (`allowTableNodeSelection` is off), which is what the user sees.
- A code fence may be indented by up to 3 spaces, and marked keeps that indent in the `code` token's `raw`. The stock `CodeBlock.parseMarkdown` accepts only a `raw` starting with the fence itself and returns nothing otherwise, so an indented fence was deleted with its code on the first save, at the top level or one column deeper than its list item's content. `parseCodeBlockMarkdown` (`codeBlockMarkdown.ts`) admits a fence after 0-3 spaces, which with indented code is every `code` token marked emits, and removes a `~~~` fence's indent from its lines as CommonMark does, since marked 17 compensates backtick fences only. `MermaidCodeBlock` and the kit's code block (`NotenCodeBlock`, swapped in by `NotenStarterKit`) both use it; keep it on any new code-block extension, and re-check it against `@tiptap/extension-code-block` and marked's `fences` on an upgrade.
- A code block's fence must outgrow every backtick run that starts a line of its code. The stock `CodeBlock.renderMarkdown` always writes three backticks, and a line of ``` in the code (or a longer run, or one after up to 3 spaces, with or without trailing spaces) is a closing fence: the next load ended the block there and read the rest of the code as Markdown, at the top level, in list items and in quotes alike. `renderCodeBlockMarkdown` (`codeBlockMarkdown.ts`) writes one backtick more than the longest run of 3 or more starting a line after 0-3 spaces; a run followed by other text (```` ```js ````) cannot close the fence but still counts, which only lengthens it, while a `~~~` line or a run 4 spaces in does not count. Code with no such line keeps the stock three backticks byte for byte, so notes without one are unchanged. `MermaidCodeBlock` and `NotenCodeBlock` both use it, next to `parseCodeBlockMarkdown`.
- Mermaid diagrams are `mermaid` code blocks rendered by the `MermaidCodeBlock` NodeView; keep its source/preview toggle and SVG/PNG export controls inside the NodeView. User-visible Mermaid labels go through `src/i18n.ts`.
- Exported SVGs round-trip their source: `mermaidExport.ts` embeds the original Mermaid source via `embedMermaidSourceInSvg` (`src/extensions/mermaidSourceMetadata.ts`, stored in `<metadata>` under a private namespace), and `ImageDrop.ts` restores a marked SVG back into an editable Mermaid block via `extractMermaidSourceFromSvg`.
