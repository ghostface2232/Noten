Invariants for the Tiptap editor layer: Markdown serialization and parsing, ProseMirror plugins and decorations, wiki/anchor links, images, tables and Mermaid, and the off-screen block skipping that keeps typing cheap in large notes.

## Editor and Markdown

- The Markdown string is the serialization format and single source of truth on disk. A single persistent Tiptap v3 instance with `@tiptap/markdown` provides WYSIWYM editing, and stays readonly until the first document loads.
- Use the official `@tiptap/markdown` API only: `editor.getMarkdown()`, `editor.commands.setContent(value, { contentType: "markdown" })`, and `contentType: "markdown"` at init. Do not use community-package APIs such as `editor.storage.markdown.getMarkdown()`. Import menus from `@tiptap/react/menus` and `Markdown` from `@tiptap/markdown` — v3 paths, not v2 examples.
- Markdown is cached in `useMarkdownState.markdownRef` (`getCachedMarkdown` / `primeMarkdown`). Tiptap's `onUpdate` marks the cache stale; `scheduleAutoSave`'s `createSnapshot` refreshes it. Any imperative content load must call `primeMarkdown(md)` — `resetDocState` does this centrally.
- `TiptapEditorHandle.openDocument({ noteId, filePath, markdown, reason })` is the normal load/switch path; it restores a cached per-document ProseMirror `EditorState` when the Markdown signature still matches, keeping at most 20 sessions for selection and undo history. `setContent(md)` is the fallback wrapper. Call `invalidateDocumentSession(noteId, filePath)` before a deleted or identity-invalid session could be reused.
- The `Markdown` extension must stay configured with `createFastMarked()` from `src/extensions/fastMarkdownLexer.ts`. Stock marked's inline lexer is O(n²) on a single large block dense with code spans, links, HTML, or escapes — a multi-million-char note on one line froze the app for minutes. `FastLexer` builds the inline mask in one linear pass and its output is byte-identical, so do not revert to the bare extension. `fastMarkdownLexer.test.ts` fuzzes token-tree equivalence against stock marked; when a marked upgrade reshapes `Lexer.inlineTokens`, re-transcribe only the main tokenization loop. `createFastMarked()` also wraps the block tokenizers Tiptap registers (`boundedBlockTokenizers.ts`): `taskList`, `orderedList` and `table` each began by splitting the entire remaining document, which made parsing O(blocks × length) — 8.7 s of a 9.4 s load for a 1 MiB note. Each wrapper hands its tokenizer a prefix ending at a line the original is proven to stop at, so the token it returns, `raw` included, is unchanged; the cut rules are argued in that file's comments and fuzzed for equivalence, and a Tiptap upgrade that changes one of those tokenizers needs its rule re-checked. Inline `start` callbacks built with `firstIndexOf(needle)` are remembered per block instead of rescanning the paragraph for every text token. Finally, a blockquote ending in an `a.`/`iv.` list re-lexes it through marked's built-in `list` tokenizer, which cannot read those markers and made the note fail to open; the instance falls back to Tiptap's `orderedList` tokenizer there.
- `editor.getMarkdown()` is replaced by the incremental serializer in `IncrementalMarkdown.ts`: each top-level block's Markdown is cached against the pair (block node, previous block node), so autosave, note switches and export re-render only the blocks a change touched (1 MB cost 80-130 ms per pause in typing before). The result must stay byte-identical to the stock serializer, which `IncrementalMarkdown.test.ts` fuzzes. It relies on `@tiptap/markdown` internals — the document renderer joining children with `"\n\n"`, and a top-level renderer reading nothing but its node and `previousNode` — so re-check both on every upgrade. Install it in `onBeforeCreate`; Tiptap v3 emits `onCreate` asynchronously, so anything hooked there misses the first call. After an edit settles, a `requestIdleCallback` pass fills the cache for blocks other than the one being edited; a block that throws there is left to the save that reports it.
- Clipboard `text/plain` goes through `sliceToPlainText` (`src/utils/clipboardText.ts`), joining block boundaries and hard breaks with a single `\n` so pasted text matches the on-screen line count. Only `text/plain` is overridden — `text/html` stays with ProseMirror, so rich targets keep formatting and in-app paste round-trips via `data-pm-slice`.

## Editor Decorations

Per-keystroke work in the editor must be incremental — no plugin or observer may re-derive whole-document state on every transaction:

- Focus mode (`FocusMode.ts`): per-selection cost is constant regardless of document size. The plugin never walks the document (no `doc.descendants` on any path); the current block's boundaries come from the resolved selection head (`$head.before(1)` / `$head.after(1)`). The decoration set holds at most one node decoration; same-block caret moves return the previous plugin state by reference, and same-block edits remap through `tr.mapping`. Dimming every other block is pure CSS. The active flag lives in extension storage so it survives `view.updateState()` note swaps, which emit no transaction.
- In-editor find (`SearchHighlight.ts`): `findSearchMatches` is the single match finder shared by `SearchBar` and the plugin. The full match list backs the counter, next/prev, and replace-all, but only `SEARCH_DECORATION_CAP` (2000) decorations are drawn — `selectMatchesToDecorate` picks those nearest the visible range, fed by a scroll-driven plugin `view`. Keep the count truthful and the drawn set bounded; do not decorate every match.
- Code-block highlighting (`incrementalLowlight.ts`): `MermaidCodeBlock` filters the stock lowlight plugin out of its inherited plugins (`isStockLowlightPlugin`, matched on the plugin key `lowlight$…`) and installs an incremental one in its place — the stock plugin walks the whole document on every transaction and re-highlights every code block whenever the selection sits in one (3.3 s per key in a 1 MiB note). Changed blocks are found by node identity and checked against the mapping, and each block's highlight is cached per immutable node. The filter is pinned by a test asserting no stock plugin survives; if a `@tiptap/extension-code-block-lowlight` upgrade renames its key, fix the matcher rather than letting both highlighters run.
- Wiki-link "missing link" decorations (`WikiLink.ts`): a target's existence changes only via the forced refresh meta (`refreshWikiLinkDecorations`, dispatched from `App.tsx` when the docs/title set or locale changes), so a plain edit remaps the existing `DecorationSet` and recomputes only the changed range. `findDocByTitle` is O(1) via a title map cached per `docs` array reference.
- Anchor links (`AnchorLink.ts` + `src/utils/headingSlug.ts`): a link mark whose href starts with `#` jumps through the same `handleOutlineJump` path the outline panel uses. Fragment resolution walks the document only at click time and once per link-popover session for `#` autocomplete — never per transaction. The popover stores GitHub-style slugs (`#서론-개요`) so serialized destinations never contain spaces, but `resolveHeadingFragment` stays tolerant of raw titles and percent-encoding — on-disk markdown is never rewritten to conform.

## Off-screen Blocks

Chromium's per-keystroke and per-IME-composition cost grows with the whole contenteditable, so DOM-heavy top-level blocks (lists, code blocks, tables) are skipped off screen with `content-visibility: auto` (`OffscreenBlocks.ts` + the "Off-screen skipping" CSS in `tiptap-editor.css`).

- Paragraphs and headings are skipped too, but only while the note has at most `MAX_TEXT_SKIP_BLOCKS` top-level blocks (the plugin's second root class, `noten-skip-offscreen-text`). Every IME composition update counts characters from the start of the editor to the caret, and Chromium's text iterator does not enter a skipped block, so unskipped prose made Hangul cost grow with the text before the caret (61 ms per update at the end of a 1.1M-character note, 17 ms with prose skipped). Every skipped element also costs the browser per frame, and re-enabling skipping after a measuring frame grows steeply with their count, so past the limit (20,000 paragraphs: typing and scrolling slower, seconds per re-measure) prose keeps its normal layout until the note is `TEXT_SKIP_HYSTERESIS` blocks back under it — its containment rides on the same class, so crossing either way re-measures, and the gap keeps Enter/Backspace at the limit from re-measuring on every key. Opening a note through `openDocument`'s `view.updateState` path builds a new plugin view, which starts from the plain limit; the `setContent` fallback keeps the current one. Below the limit the price is a few ms of typing latency (p50 and p95) and scroll frames. A test pins `SKIPPABLE_BLOCK` / `SKIPPABLE_TEXT` to the stylesheet's selectors. Keep the CSS selector and `SKIPPABLE_TEXT` identical.
- Skipped sizes are never guessed: `contain-intrinsic-size: auto` remembers each block's rendered size, and the plugin drops its root class for a frame (a full layout) whenever sizes could be missing or stale — an off-screen skippable block created or changed (except the block holding the caret when the update scrolls to it and the editor has focus, so the scroll happens: plugin views run before ProseMirror's scroll, so Enter on the last visible line would otherwise re-measure the whole note), a width change, a web-font load, or a typography setting (`remeasure()`). A new layout input that changes block heights must call `editor.storage.offscreenBlocks.remeasure()`, or jumps, find and the scrollbar land off target.
- The containment is applied permanently (not only while skipped), so a block measures the same either way. It stops a list's last-item margins from collapsing out of the list; the list margin rules next to it compensate exactly and are layout-neutral without containment. Blocks whose content changes height asynchronously (images, Mermaid) or holds larger escaping margins (rule, heading, quote in a list) are excluded and keep today's layout. Keep the CSS selector and `SKIPPABLE_BLOCK` identical.
- Check layout changes here with `node bench/run.mjs --geometry` against the previous build and `--nav` (see `bench/README.md`).

## Wiki Links and Titles

`[[Title]]` names its target by title alone, so duplicated titles need one agreed resolution rule, shared by every consumer:

- `findDocByTitle` orders candidates by `createdAt` ascending with the note id as tiebreaker — never by position in `docs`, which is the sidebar sort order (under the default `updated-desc`, editing one of two same-titled notes would otherwise silently re-point every link at it).
- When the link's own note is in a group, a candidate in that same group wins. `findDocsByTitle` exposes the full candidate list for ambiguity checks.
- The click handler resolves the target and hands `navigateToDoc` an **id**. Do not re-resolve a title on the App side; two lookups can disagree.
- `renameNote` skips back-link rewriting entirely when the OLD title was shared by another note: `[[Old]]` cannot be attributed to one target, and rewriting would re-point links belonging to the other note. It returns `RenameNoteResult.linkRewriteSkipped` and App.tsx surfaces the transient notice.
- `normalizeNoteTitle` (`src/utils/noteText.ts`) is the single definition of "same title" for link resolution, duplicate detection, and rename.
- `customName` on a document means the user manually renamed it; auto-title derivation is permanently disabled for that document.

## Images

- Image sources are note-local relative asset paths (`.assets/<noteId>/<hash>.<ext>`) on insert, replace, drop, and paste. Legacy base64 is still accepted (`allowBase64: true`) and migrated on startup once per notes directory.
- Image NodeViews share one per-editor `transaction` subscription (`registerImageSelectionSync` in `ImageView.ts`) that re-syncs selection outlines only when the node-selected position or readonly flag changes. Do not re-add a per-NodeView `editor.on("transaction")` listener — that made selection bookkeeping O(images) on every keystroke.
- Editor images load their `.assets/` file through the app's `noten-asset` URI scheme (`resolveRenderableImageSource` → `convertFileSrc(path, "noten-asset")`), the way Obsidian's `app://` or Joplin's `joplin-content://` do: the browser reads, caches and evicts the image itself. Do not go back to reading assets into JS — base64 data URLs cost ~15 s of main thread for a 600-image note, and Blob URLs hit WebView2's Blob storage limit and left images broken. The scheme is served by `note_asset_response` in `src-tauri/src/lib.rs` on a blocking worker, not by Tauri's built-in asset protocol, which reads on the UI thread (an OneDrive file still downloading would freeze the window and all IPC). Build paths with `/`. The headless PDF renderer cannot load the scheme, so PDF export points those images at their files as `file:` URLs (`pointAssetImagesAtFiles`, `fileUrlForPath`); it prints the export HTML from a `file:` page and loads them itself. Do not inline them as data URLs again: the HTML then holds every image at once, and a note with ~500 MB of images passed the JS string limit and printed a blank page. Which file an image may point at is decided by the Rust command `note_image_files`, which applies `is_servable_note_image` to canonical paths, so the PDF can never show a file the editor would refuse. Edge still decodes every image in one renderer: a note with ~500 MB of images needs ~10 GB and fails with an explanation (`failure_reason`); a 60-image note (48 MB) exports in ~12 s and a 300-image one (240 MB) in ~65 s.
- Image Markdown serialization must use `serializeImageMarkdown` so `src`, `alt`, and `title` are escaped correctly for their Markdown/HTML context. When `width`/`height` are set, `renderMarkdown` emits `<img>` HTML to preserve dimensions through round-trips.
- On insert, images are capped to 560px width via `clampImageDimensions`. Height is always `auto` in CSS — only width is set in px, to prevent aspect-ratio distortion on narrow viewports.
- `createImageNodeView` owns resize handles, drag reorder (6px `pointerdown` threshold → `startReorder()`, single undo step), context menu, and asset-source rendering. Ctrl+C on a selected image copies the image blob, not HTML.

## Tables and Mermaid

- Tables use Tiptap v3 table extensions with `lastColumnResizable: false`, so dragging an inner column redistributes width instead of growing the table past the editor width.
- Empty table cells may serialize through `&nbsp;`; `stripTableCellNbsp` removes placeholder-only leakage before load/save while preserving a user-authored literal `&nbsp;`.
- Mermaid diagrams are `mermaid` code blocks rendered by the `MermaidCodeBlock` NodeView; keep its source/preview toggle and SVG/PNG export controls inside the NodeView. User-visible Mermaid labels go through `src/i18n.ts`.
- Exported SVGs round-trip their source: `mermaidExport.ts` embeds the original Mermaid source via `embedMermaidSourceInSvg` (`src/extensions/mermaidSourceMetadata.ts`, stored in `<metadata>` under a private namespace), and `ImageDrop.ts` restores a marked SVG back into an editable Mermaid block via `extractMermaidSourceFromSvg`.
